# ADR-0039: The daemons apply the Maxine SDK environment to themselves, and the Arch build is one package per loadable module

- **Status:** Accepted (2026-11-15), implemented in 0.54.0 (`crates/obc-core/src/sdk_env.rs`, `crates/omarchy-broadcastd`, `crates/omarchy-broadcast-audiod`, `packaging/arch/PKGBUILD`, the omarchy-onnx-models repository's `packaging/arch/PKGBUILD`). No D-Bus member is added and the module interface does not change. Amends [ADR-0012](0012-video-effects-and-maxine-backend.md) and [ADR-0021](0021-nvidia-sdk-handover.md) (the systemd drop-in that preloaded the os-release shim, and the optional dependency on the SDK package, are replaced), [ADR-0031](0031-onnx-cutout-module.md) (the separate `packaging/arch-onnx/` recipe, with the models as its sources, is replaced by a module package and one package per model), and [ADR-0025](0025-loadable-modules.md), [ADR-0028](0028-maxine-ar-module.md) and [ADR-0029](0029-audio-modules-mic-host-and-worker.md) in the points listed under "Amendments". Reference: [../setup/maxine.md](../setup/maxine.md#3-the-sdk-environment), [../setup/microphone.md](../setup/microphone.md#the-workers-sdk-environment), [../setup/onnx.md](../setup/onnx.md#3-install-the-module-and-the-models), [../testing.md](../testing.md#the-sdk-environment-of-the-daemon-and-the-audio-worker).

## Context
- The NVIDIA Maxine SDKs are personal downloads that the user packages with the omarchy-nvidia-sdks repository (`maxine-vfx-sdk-local`, `maxine-ar-sdk-local`, `maxine-afx-sdk-local`). Each package installs an environment file in `EnvironmentFile=` syntax (`/usr/share/maxine-<x>/maxine-<x>.env`) and an os-release shim (`/usr/lib/maxine-<x>/os-release-shim.so`). The SDK's model loader accepts only the distributions NVIDIA lists, and the shim, preloaded, shows the process a replacement `os-release` ([ADR-0012](0012-video-effects-and-maxine-backend.md), [ADR-0021](0021-nvidia-sdk-handover.md)).
- `LD_PRELOAD` (and `LD_LIBRARY_PATH`) take effect only when a process starts, so until now the environment came from a systemd drop-in that the user copied by hand from an example (`omarchy-broadcastd.service.d/maxine.conf`, `omarchy-broadcast-audiod.service.d/maxine-afx.conf`, and a hand-written one for the AR SDK on a machine without the Video Effects package). It was a manual step that users missed, whose failure looked like an SDK error (`-1209`, "no kernel image is available"), and that had two ways to go wrong: with `EnvironmentFile=` unprefixed a missing package failed the unit, with the `-` prefix the dynamic linker logged an unloadable shim at every start.
- The Arch build made one package, with the Maxine VFX, AR and AFX modules and the CPU voice module in it, the SDK packages as optional dependencies, and a second recipe, `packaging/arch-onnx/`, for the ONNX module. A user who wanted no NVIDIA software still got modules that were listed as unavailable; a module could be installed without the SDK it needs.
- The ONNX recipe took the four model files (about 70 MB) as sources of its build. A `-git` package is rebuilt at each commit, so each rebuild downloaded them again. The four models also carry their own licence and notice, which a single package mixes.
- The two recipes had to be kept at one version (`scripts/check-all.sh` compared the `pkgver` of both with `Cargo.toml`), and the second built on the committed HEAD of the first.

## Decision
**The daemon and the audio worker detect the SDK package that matches them when they start, apply its environment to themselves and execute themselves once; no drop-in is needed. The Arch build is one split package: the core and one package per loadable module, each module depending on the SDK or the runtime it needs. The ONNX models are one package per model, from the omarchy-onnx-models repository.**

### The SDK environment is applied by the process
- **What each process considers.** `omarchy-broadcastd`: the Video Effects SDK, then the AR SDK (its module runs in the daemon and needs the same shim). `omarchy-broadcast-audiod`: the Audio Effects SDK. An SDK is *complete* when both its environment file and its shim exist.
- **How.** Before any thread starts, the process reads the environment files of its complete SDKs, merges them into its environment by the rules below, sets the marker `OBC_SDK_ENV_APPLIED` (the files applied, separated by `:`) and executes itself again: the path of its own executable (`std::env::current_exe`, so the process keeps the name of the binary), the same arguments, the same PID (an `exec`), so a socket that systemd handed over (`LISTEN_FDS`) is still the process's. The process that finds the marker is the one executed again: it logs `SDK environment applied from <file>[, <file>]` and removes the marker, so the programs it starts decide for themselves.
- **Why a second run.** `LD_PRELOAD` takes effect when the dynamic linker maps the process. The shim must interpose `fopen`, `open` and the like, which the C library has already bound in a running process, so a shim opened later by `dlopen` would not intercept the SDK's reads of `/etc/os-release`.
- **Why this re-execution is acceptable now.** The amendment of [ADR-0021](0021-nvidia-sdk-handover.md) rejected a daemon that executes itself with `LD_LIBRARY_PATH` set, for the cost of a second start and for the unit and D-Bus activation: the process that owns the bus name and the one systemd tracks must be the same. The call is the first thing `main` does (after reading the command line), before any thread, the bus connection or the socket the worker listens on, and it is an `exec`, not a new process: the PID is the one systemd tracks, and the bus name is requested only by the second run. What remains of the cost is one `exec` of a program that has initialised nothing.
- **The merge rules** (`sdk_env::decide`, a pure function: it takes the environment, the files and whether a shim is mapped as arguments, so every case is unit-tested without executing anything):
  1. A variable already set in the inherited environment is never overwritten: an explicit setting wins.
  2. `LD_PRELOAD` gets the shim of the first complete SDK appended (`:` separated), unless it already names it. Exactly one shim is preloaded; the `MAXINE_OS_RELEASE` applied is that SDK's, and a later complete SDK contributes its other variables only.
  3. `LD_LIBRARY_PATH` is applied by the audio worker only: its own entries first, then the file's entries not already present. The Audio Effects SDK opens its feature libraries by a name that only the library search path resolves. `omarchy-broadcastd` never applies it: the video modules load the SDK's libraries by absolute path, and the SDK's bundled CUDA 12 and TensorRT 10 on the daemon's search path would be found by the other modules of the process too, and shadow the engines of ONNX Runtime.
  4. No SDK root (`MAXINE_VFX_ROOT`, `MAXINE_AR_ROOT`, `MAXINE_AFX_ROOT`) is applied. A root variable took precedence over `sdk_root` in the configuration ([ADR-0021](0021-nvidia-sdk-handover.md), amendment), so applying the package's would have ignored the key for every user of the package. The modules' default root is the package's anyway.
  5. Every other dynamic loader variable of the file (`LD_*` but `LD_LIBRARY_PATH`, and `GCONV_PATH`) is refused, whatever the file holds: a file read at the start of a process must not be able to preload code of its own choosing. Every other variable is applied when it is unset (`MAXINE_OS_RELEASE`, the feature list).
- **When nothing is done.**
  - `OBC_NO_SDK_ENV` is set to a non-empty value other than `0`: the opt-out, for debugging and for the tests that start the binaries.
  - The marker is set: this is the second run.
  - A shim of the profile, or any mapped library named `os-release-shim.so`, is already in the process (a unit or a drop-in of the user's preloads it; the shim removes `LD_PRELOAD` from the environment when it loads, so the variable cannot tell, and the process reads its own memory map). It logs `SDK environment already in place (the os-release shim is loaded): not applied again`. This keeps an SDK tree without a package, and a drop-in copied for an earlier version, working.
  - An SDK has neither file: skipped silently (a debug line). It has one of them, or its environment file cannot be read or parsed: one warning that names the file (and the line, for a parse error) and ends `running without its environment`; the process runs without that SDK, the other SDK of its profile may still apply, and nothing is executed again for it. The module then reports as before that the SDK is not installed or that the shim is missing.
  - Executing again fails: a warning, and the process runs without the SDK environment.
- **The packaged unit files do not change.** The drop-in examples `maxine.conf` and `maxine-afx.conf` are removed from the repository and from the package (the WirePlumber drop-in is unrelated and stays). `scripts/install-user.sh` no longer offers drop-ins; it prints how to remove one that is still there.
- **Reason strings.** The reasons that named the drop-in (the Maxine module's `-1209` hint, the AR module's, and the Audio Effects module's `REASON_NO_SEARCH_PATH`) now name the SDK package and `OBC_NO_SDK_ENV`.

### One package per loadable module
`packaging/arch/PKGBUILD` is a split `pkgbase` of five packages from one build. Each module depends on the core of the same build (`omarchy-broadcast-git=<pkgver>-<pkgrel>`), as the module interface is not pinned across versions, and each `-git` package provides and conflicts with its non-git name, as the core always did.

| Package | Contents | Depends |
|---|---|---|
| `omarchy-broadcast-git` | the daemon (the CPU video path is part of it, there is no separate CPU video module), the client, the audio worker, the CPU voice module, the mic host's configuration and LADSPA plug-in, the units, the D-Bus files, the udev rule, the media, the module header, the documentation and the licences | what the core needs |
| `omarchy-broadcast-maxine-vfx-git` | the Maxine VFX module and its manifest | the core, `maxine-vfx-sdk-local` |
| `omarchy-broadcast-maxine-ar-git` | the Maxine AR module and its manifest | the core, `maxine-ar-sdk-local` |
| `omarchy-broadcast-maxine-afx-git` | the Maxine AFX audio module and its manifest | the core, `maxine-afx-sdk-local` |
| `omarchy-broadcast-onnx-git` | the ONNX cut-out module and its manifest, no models | the core, `onnxruntime>=1.29`, `omarchy-onnx-model-mediapipe-landscape`; optional: the other model packages and the engines by their virtual names (`onnxruntime-provider-cuda`, `-tensorrt`, `-openvino`) |

The core lists the module packages as optional dependencies. `packaging/arch-onnx/` is removed. Every package installs the project's licences and `THIRD-PARTY-NOTICES`, which names the libraries each binary statically includes (the core and each module library: `libloading` is linked into the daemon, the worker and the four SDK and ONNX module libraries, not into the CPU voice module).

The Maxine module packages depend on the SDK packages by name, a hard dependency. [ADR-0021](0021-nvidia-sdk-handover.md) rejected one on the single package, because most of the project works without the SDK; with a package per module the dependency is the module's, and a user without the SDK does not install the module.

### One package per model
The omarchy-onnx-models repository builds, from its `packaging/arch/PKGBUILD`, one package per model of its catalogue: `omarchy-onnx-model-mediapipe-landscape` (the default), `omarchy-onnx-model-pphumanseg-v2-mobile`, `omarchy-onnx-model-pphumanseg-v2-lite` and `omarchy-onnx-model-modnet`. The version is the repository's release (1.0.0), the sources are that release's assets, each checked against the release's SHA-256, and each package installs its one `.onnx` file in `/usr/share/omarchy-onnx-models/` with its licence and `NOTICE` in `/usr/share/licenses/<package>/`. The path is neutral to omarchy-broadcast so that other programs can use the models.

The ONNX module's search order is now: `model_dir` of its configuration; `$OBC_ONNX_MODEL_DIR`; `$XDG_DATA_HOME/omarchy-broadcast/models/onnx/`; `/usr/share/omarchy-onnx-models/`; `/usr/share/omarchy-broadcast/models/onnx/` (kept for installs of the earlier package). The first directory that has the file wins, and the SHA-256 check at load is unchanged: a wrong file in an earlier directory fails the load and is not skipped. A missing model's message names the package to install.

## Consequences
- Maxine works after the packages are installed and the daemon restarted: no file is copied, no `daemon-reload`. The log says what was applied (`journalctl --user -u omarchy-broadcastd | grep 'SDK environment'`), which is also the first thing to check when an effect fails with `-1209`.
- A drop-in copied for an earlier version still works (its shim counts as in place), but it is not needed, and an old `maxine.conf` whose `EnvironmentFile=` has no `-` fails the unit once the SDK package is removed. The documentation says to remove it.
- The SDK package's `LD_LIBRARY_PATH` reaches only the audio worker, whose CPU voice module uses neither CUDA nor TensorRT. The daemon runs without it, as before: the SDK's bundled libraries are loaded by the modules by absolute path.
- A user's own tree of an SDK (no package) still needs a drop-in of their own, with the shim and `MAXINE_OS_RELEASE`; because the process recognises the shim in its memory map, the two paths do not interfere.
- Two processes start where one did, for a process that applies an environment. The second run is the same program, so the cost is one `exec`; the process name and the PID are those of the first.
- The Maxine modules are no longer in the core: a machine without NVIDIA software has no Maxine modules to list as unavailable, and the bar plug-in's existing "Not installed" greying covers a module that is not there. A user who installs the core alone has the CPU video path and the CPU voice module.
- A rebuild of the `-git` core no longer downloads the models. A new model release changes one repository and its packages, not omarchy-broadcast. Each model's licence is installed with it, and removing a model removes its licence.
- The tests that start the daemon or the worker set `OBC_NO_SDK_ENV=1` (`docs/testing.md`), so a developer's installed SDK is not applied to the process under test; `check()` still removes the SDK variables from `cargo test`.
- `THIRD-PARTY-NOTICES` was corrected as part of this change: the daemon and each SDK and ONNX module library statically include `libloading` 0.8.9, and the ONNX module also 0.9.0 (its own use and `ort`'s), not only the audio worker.

### Known limits
- **The environment is applied at start only.** A package installed while the daemon runs applies at its next start (the audio worker starts on demand, so at the next microphone use); a reload does not re-run it.
- **One shim per process.** With the Video Effects and AR SDKs both installed the daemon preloads the Video Effects shim and the AR file contributes its other variables only. The two shims do the same, and the SDKs themselves load side by side ([ADR-0028](0028-maxine-ar-module.md)).
- **A half-installed SDK is skipped, not repaired.** The warning names the file; reinstalling the package fixes it.
- **The module packages cannot be installed without the SDK.** A developer who wants a module without its SDK installs it from a checkout (`scripts/install-user.sh`).

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **Keep the drop-ins, copied by hand** | The failure was silent and looked like an SDK error, and the instructions had to be kept for two units and three SDKs. The information needed (two paths) is in the packages and the process can read it |
| **Ship the drop-ins active in the packages** (in `/usr/lib/systemd/user/<unit>.d/`) | A drop-in of the core cannot depend on whether an SDK package is installed: with `EnvironmentFile=` unprefixed the unit fails without the package, and with the `-` prefix the dynamic linker logs an unloadable shim at every start. One shipped by a module package would work for that module's SDK only, would need a drop-in per SDK, and would still leave the checkout installs and an SDK tree without a package to hand-written drop-ins |
| **`dlopen` the shim at run time** | The shim works by interposing libc's `open` and `fopen` for the SDK's reads of `/etc/os-release`. A library opened after the process started does not replace symbols that the process and the libraries loaded so far have bound, so it would not catch the SDK's reads. `LD_PRELOAD` must be in place when the process starts, which means executing again |
| **Apply `LD_LIBRARY_PATH` in the daemon too** | The SDKs bundle CUDA 12 and TensorRT 10. On the daemon's search path every module of the process would find them first, ahead of the system's CUDA 13 and the engines of ONNX Runtime. The video modules load the SDK from its root by absolute path and need no search path. The worker needs it and its modules use neither library |
| **Apply the SDK root variables from the file** | `MAXINE_*_ROOT` outranks `sdk_root` in the configuration, so the key would stop working with the package installed. The default root is the package's already |
| **Apply the whole file, loader variables included** | The file is trusted as a package file, but a process that reads a file at its start and puts `LD_*` or `GCONV_PATH` from it in its environment lets that file choose what is preloaded or which conversion module loads. Only the library path and the one shim are needed |
| **One package, the modules as optional dependencies** | A module could be installed without the SDK it needs and listed as unavailable; the SDK stays an optional dependency of a package that does not use it; the ONNX Runtime variants, which conflict with one another, cannot be a dependency of the core. A package per module makes each dependency exact |
| **One `PKGBUILD` per module** (the earlier `packaging/arch-onnx/` generalised) | Each recipe would build the workspace again, and each `pkgver` would have to be kept in step with `Cargo.toml` and with the core it depends on, as `scripts/check-all.sh` did for two. A split package builds once, at one version |
| **The models inside the `-git` build** | About 70 MB downloaded again at every rebuild, and four licences and notices in one package, though a user may want one model |
| **The models as one separate package** | One package still brings every model and every licence; the default model is the one most users want and the others are choices |

## What would change this decision
- A change in the SDK packages' layout (their paths, their environment file's syntax or the variable names): `sdk_env` follows them, and its tests that parse the package files say so.
- An SDK whose loader no longer reads `/etc/os-release`, or a loader that honours another way to name the distribution: the shim, and with it the second run, would go.
- A redistributable SDK: the module packages could contain it, and the environment would be set by the package.

## Amendments
- [ADR-0012](0012-video-effects-and-maxine-backend.md), [ADR-0021](0021-nvidia-sdk-handover.md): the drop-in is replaced by the process applying the environment; the optional dependency is replaced by the module package's dependency.
- [ADR-0025](0025-loadable-modules.md): the modules the Arch build installs are packages of their own; manifests are still read from the same directories.
- [ADR-0028](0028-maxine-ar-module.md): the AR module needs no drop-in, and the daemon applies the AR package's environment (after the Video Effects one).
- [ADR-0029](0029-audio-modules-mic-host-and-worker.md): the audio worker applies the Audio Effects SDK's environment to itself, `LD_LIBRARY_PATH` included.
- [ADR-0031](0031-onnx-cutout-module.md): the ONNX module and its models are no longer built from `packaging/arch-onnx/`.
