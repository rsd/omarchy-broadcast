# ADR-0026: A configuration directory and a daemon-managed drop-in, with a config schema

- **Status:** Accepted (2026-11-10), implemented as phase 2 of the module system: daemon 0.25.0, D-Bus revision 10. Amends [ADR-0007](0007-headless-daemon-toml-config.md) and [ADR-0011](0011-daemon-lifecycle-and-dbus-api.md) (the configuration is no longer one file the daemon never writes: it is a set of files, one of which the daemon manages) and [ADR-0025](0025-loadable-modules.md) (the module choices move from the state file to the configuration). Builds on [ADR-0023](0023-settings-schema.md) (the config schema uses the same self-describing row model as the settings). Reference: [../dbus-api.md](../dbus-api.md#configuration-revision-10), [../cli-json.md](../cli-json.md#config), [../config.example.toml](../config.example.toml).

> *Amended by [ADR-0029](0029-audio-modules-mic-host-and-worker.md): the daemon also writes the audio settings snapshot (`audio-settings.json` in the state directory) for the audio worker, and the `[mic]` table joins the config schema. `config.d/50-panel.toml` stays the only configuration file it writes. The text below is the original decision.*

## Context
- Until now the configuration was one file, `config.toml`, that only the user edited, and the daemon never wrote ([ADR-0007](0007-headless-daemon-toml-config.md), [ADR-0011](0011-daemon-lifecycle-and-dbus-api.md)). What a user chooses at run time (on or off, the camera, the effect, a module's settings) went to a separate state file. The split keeps `config.toml` free of rewrites, so that its comments and layout stay as the user left them, and it can be kept in version control.
- The module system ([ADR-0025](0025-loadable-modules.md)) added choices that are durable and that people share between machines: which modules are enabled, the stage order, the backend profile and the pins. Phase 1 kept them in the state file, over the configuration's `[modules]` keys, so the same key could have two homes and a client could not tell which one was in force.
- A setup dialog in the bar needs to change daemon configuration (the output format, the idle grace, the module choices), show where each value comes from and say when a change takes effect. Clients carry no knowledge of the keys ([ADR-0023](0023-settings-schema.md)): the daemon has to describe them.
- A user who writes a setting by hand must stay in charge. If a hand-written file sets a key, the dialog must not appear to change it.
- Revision 9 clients and the CLI keep working against a revision-10 daemon, and the other way round ([../dbus-api.md](../dbus-api.md#versioning)): the change is additive.

## Decision
**The configuration is `config.toml` followed by the files of `config.d/`, merged key by key. The daemon writes exactly one file of the set, `config.d/50-panel.toml`, on behalf of the setup dialog, the CLI and D-Bus clients; it never writes `config.toml` or any other file. The daemon publishes a config schema that says, for each key, its value, which file set it, whether it can be changed through the daemon and when a change applies.**

### The configuration is a set of files
- **Files and order.** `$XDG_CONFIG_HOME/omarchy-broadcast/config.toml` (default `~/.config/omarchy-broadcast/`), then every regular file of the `config.d` directory next to it whose name ends in `.toml` and does not start with a dot, in byte order of the file name. Other names, hidden files and subdirectories are ignored; a missing `config.d` is an empty one. `--config PATH` moves the set: `config.d` is the directory next to `PATH`.
- **Each file is checked alone first.** An unknown key (as before, every key is checked and unknown ones are errors), a value of the wrong type or out of range is reported with that file and its line (the message starts `<dir>/config.d/90-local.toml:3:1: ...`). The checks that span keys run on the merged result, and an error there names the last file that set the key.
- **Deep merge.** Tables are merged key by key, so a later file can change one key of a table another file set. Any other value, a scalar or an array, is replaced whole by the later file: a later `modules.order`, `camera.preference` or `modules.disabled` is not appended to the earlier one. `modules.pin.<stage> = ""` is "automatic" and, in a later file, clears the pin of an earlier one.
- **One bad file rejects the set.** As for a single file before, the previous configuration stays in force, the `Error` property names the file and line, and nothing is half-applied. `SIGHUP` and `ReloadConfig` read the whole set again; the daemon does not watch the directory.
- **Provenance.** For every key the loader records the file that set the value in force (none: the default). It is what the config schema reports as `source`, and what decides whether a key is overridden (below).

### The managed file, `config.d/50-panel.toml`
- **Why a file in the middle of the order.** `50` leaves room on both sides. A file named before it (`10-`, `40-`) gives a default that a change through the daemon replaces; a file named after it (`90-local.toml`) wins over what the dialog writes, so a hand-written override is never silently undone.
- **What the daemon writes.** Only the keys written through the daemon (`SetConfig` and the four module setters). The file is regenerated whole from the daemon's table on every write, after a header that says it is managed and tells the user where to put their own settings. It is written atomically: a temporary file in the same directory, flushed, renamed over the file, and the directory flushed; `config.d` is created when needed. An edit that changes nothing writes nothing.
- **A write is checked before it is made.** The new merged configuration is validated as a load would validate it, then the file is written, then the result is applied as a reload would apply it, restarting only what the key needs; clients are told with `ConfigChanged`. If reading the set back fails after the write (a file changed meanwhile), the write is not undone and the set that was checked is the one in force.
- **What the daemon refuses to write.** A key that is unknown, or that is not one of the editable keys (see below); a key that a file after `50-panel.toml` sets (the refusal reads "Overridden by config.d/90-local.toml"); a value that fails the checks; a write while another file of the set does not load (nothing could be checked); a `50-panel.toml` that does not load, which is never overwritten (the user fixes or deletes it; the error names the file); and a `50-panel.toml` that is a symbolic link, which is never replaced (the user may edit the file it points to).
- **`config.toml` and every other file are never written.** This is the acceptance criterion: they are byte-identical after any number of writes.

### The config schema
- `GetConfigSchema` returns groups of rows, built like the settings tree ([ADR-0023](0023-settings-schema.md)). The core keys are a table fixed at build time; the rows of the module system are made from what the registry found: `modules.enabled.<id>` for each installed module, and `modules.pin.<stage>` for each stage offered, with the modules that offer it as options.
- A row has the setting's keys (`label`, `description`, `type`, `value`, `default`, range or options, `enabled`, `disabled_reason`) and four of its own: `source` (the file that sets the value in force), `overridden_by` (the file after `50-panel.toml` that sets it, which makes the row not enabled, with the reason "Overridden by <file>"), `editable` (whether the daemon accepts `SetConfig` for it) and `apply` (`live`, `reload` or `restart`: when a change takes effect). New row types are `float`, `string`, `path` and `list`. The settings schema version stays 1: an older client skips a type it does not know.
- **Editable keys** are those a person changes to tune the daemon and that are safe to change while it runs: `camera.fixed_framerate`, the output's `format`, `aspect`, `hold_timeout_s` and `input_gap_ms`, the lifecycle's `idle_grace_s` and `start_debounce_ms`, `effect.on_failure`, `pipewire.enabled` and `pipewire.offer_nv12`, `modules.profile`, `modules.enabled.<id>` and `modules.pin.<stage>`. The others are shown read only, so that the dialog is complete: the camera preference and mode, the output mode, the loopback's label and device, `modules.dirs`, `modules.disabled` and `effect.maxine_root` are set in `config.toml`; the `[effect]` defaults are overridden by the run-time choices of the panel, so a write to them would not show (the row's description says so); `modules.order` is changed through `SetStageOrder`, which has its own editor and persists to the managed file.
- `GetConfigFiles` lists the files in load order as they are on disk now, with their status (`loaded`, `absent`, `error` and the reason) and which one is managed, for the dialog's diagnostics.

### The module choices move into the configuration
- `[modules]` gains `enabled`, a table from module id to `true` or `false`. It is the key `SetModuleEnabled` writes. For one module it beats the `disabled` list, whichever file the list is in; modules it does not name follow `disabled`. `modules.order`, `modules.profile` and `modules.pin` already existed.
- `SetModuleEnabled`, `SetStageOrder`, `SetBackendProfile` and `SetStagePin` now write `config.d/50-panel.toml` and are refused for a key a later file sets. A clear (an empty order, an empty pin) removes the key from the managed file, or, when an earlier file sets it, writes the empty value, so that the key really is back to the default.
- **Migration.** A state file written by a phase-1 daemon holds the choices in its `[modules]` table. At the first load (and at every reload that finds some left), for each key `50-panel.toml` does not set already, the daemon writes it there, and only when that has succeeded removes the table from the state file. A crash between the two writes loses nothing: the configuration holds the choices, and the state file's copy is dropped the next time. An entry that is not valid (a malformed id, a stage twice in the order) is dropped with a warning.
- **A move that cannot be made is pending, not lost.** If `config.d` cannot be written, or the set does not load at start, the state file keeps the choices and they stay in force over the configuration, as they were in phase 1; the move is tried again at every reload and before every write of the managed file (which then goes over the moved choices). A module setter answers `Failed` with the reason while the directory is unwritable, or `InvalidConfig` while another file does not load, and changes nothing.
- **What stays in the state file.** The module settings' values (`[settings]`, for example `effect.hello.enabled`), the selected camera, the effect choices, the camera settings per camera and the crash ledger: the user's choices of the moment, which a person does not version, and which `config.toml` would only be a second home for ([ADR-0011](0011-daemon-lifecycle-and-dbus-api.md)). The run-time effect choices still override the `[effect]` keys, as before.

## Consequences
- The setup dialog and the CLI change the configuration through the daemon, and a hand-written override always wins and is shown as such. A person who never touches `config.d` sees no difference, except that module choices are in a file they can read.
- **Downgrade.** A daemon of 0.24 (revision 9) ignores `config.d`. After the migration the module choices are in `50-panel.toml` and no longer in the state file, so a 0.24 daemon falls back to what `config.toml` says about the modules: the enabled modules, the order, the profile and the pins the user chose through the panel are not seen by it. Copy them into `config.toml` before downgrading, or choose them again.
- **`modules.enabled` and `modules.disabled`.** A `modules.enabled.<id>` in `50-panel.toml` beats a `modules.disabled` list naming the same module, in `config.toml` or in a later file. Only a later file that sets `modules.enabled.<id>` itself overrides it. A user who lists a module in `disabled` after having switched it on in the dialog sees it stay on until they set the key or reset it (`omarchy-broadcast config reset modules.enabled.<id>`). The row for the module says which file set it.
- A stale entry (a module no longer installed, a stage no longer offered) cannot be set through the daemon, but can be reset: `ResetConfig` removes any key `50-panel.toml` sets.
- A change to a key that applies at the next camera start, or at the next daemon start (`apply` says which), is stored at once and does not touch a running pipeline, as the module choices never did.
- `ConfigSerial` moves when the configuration, its provenance or the file list changes, including a refused reload (the list then shows the error) and a change of the modules found, so a client reads the schema again when it differs.
- The daemon has a second kind of file it writes, with the failure modes of one: an unwritable directory, a file the user broke, a symbolic link. Each has a reason a client shows, and none stops the daemon.
- The module setting values and the typed choices of revision 8 stay where they were: a rev-8 or rev-9 daemon reading the state file keeps them.
- Known limitations:
  - The files of `config.d` are read at start, on `SIGHUP` and on `ReloadConfig`; a hand edit is not seen before one of them.
  - Free `[module."<id>"]` tables are not rows of the schema: the module validates them. They are not editable through the daemon.
  - While a move of the module choices is pending (an unwritable `config.d`, or a set that did not load at start), the schema rows show the loaded values rather than the ones the state file keeps in force.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| The daemon edits `config.toml` | A program rewriting a file a person edits by hand loses comments and layout unless it carries a format-preserving editor, and then still races the user's editor. This is why [ADR-0011](0011-daemon-lifecycle-and-dbus-api.md) moved the runtime choices out of it; a separate file the daemon owns avoids the problem and tells the user which file is whose |
| The plugin writes the files itself | The rules (what is editable, what a later file overrides, validation, which key needs a restart) would be duplicated in every client, and two writers would race. The daemon already holds the loaded configuration, the module registry and the validator; a client asks it |
| Keeping the module choices in the state file | The choices could not be described in the config schema with a source, could not be overridden by a hand-written file, and would stay invisible to someone who reads their configuration. The same key would keep two homes, with the state winning |
| A free-form text editor for the configuration in the dialog | The dialog would have to parse and validate TOML, and could not show which file wins or when a change applies. Typed rows put every rule in the daemon, which checks a value before it is written and answers with a reason; the file remains the place for anything the rows do not offer |

## What would change this decision
- A need for the daemon to change a key in a file the user wrote by hand: that needs a format-preserving editor, or a change the user approves.
- More than one managed file (for example one per client): the position of a single `50-panel.toml` would need a rule for the order between them.
