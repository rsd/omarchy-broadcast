# ADR-0023: Camera settings: a tree the daemon describes, computes and publishes

- **Status:** Accepted (2026-11-10). Extends [ADR-0020](0020-camera-image-controls.md) (per-camera storage, written whenever the camera opens, never to a closed camera) and [ADR-0011](0011-daemon-lifecycle-and-dbus-api.md) (the D-Bus API as revision 7, additive, and the runtime state file). Uses the control plane of [ADR-0005](0005-dbus-zbus-control-plane.md) and the camera's place in the ingest stage of [ADR-0009](0009-ingest-process-output.md).

## Context
- Revision 6 offers five image controls from a fixed allowlist ([ADR-0020](0020-camera-image-controls.md)). Users also want exposure, white balance, focus, zoom and anti-flicker, and a camera has more: the bar widget grew four hand-written sliders and a reset for the five, and every new control would mean a new member, a new type and new widget code in each client.
- The allowlist left those controls out on purpose. Exposure, focus and white balance have an automatic mode that makes the manual control inactive, so a list of them needs the rules between them, and ADR-0020 rejected "list every control" until that interplay was designed. V4L2 does not declare the dependencies: a camera sets an `INACTIVE` flag on the dependent control, and the flag is live only while the device is in that state.
- The widget is a Quickshell (QML) plugin. Quickshell has no generic D-Bus access: its D-Bus support is private plumbing behind fixed-purpose services (media players, the tray, UPower and the like), none of which can be pointed at another service. The plugin reaches the daemon through the CLI: a long-lived `watch --json` for what changes, and a one-shot command for each write ([cli-json.md](../cli-json.md)). Lines of that output are capped at 4096 bytes, and a rule of the JSON contract says a change to the cap is breaking.
- A camera's settings in full are 4 to 6 KB of labels, ranges, option lists and flags: more than one line holds.
- A client that carries the list of controls and the rules between them is wrong the first time a camera differs. The daemon is the one place that sees the device.
- Some settings are not V4L2 controls. The Logitech Brio and MX Brio keep their field of view (90, 78 or 65 degrees, a crop in the image processor) in a vendor UVC Extension Unit. Those cameras also carry a controllable LED in another unit, which the kernel guards as a privacy control.
- Other software changes a camera's controls while the daemon has it open, and so does the camera. ADR-0020 declined to follow those changes without polling. Subscribing to V4L2 control events needs an open file descriptor on the node, and an open descriptor keeps a UVC camera out of autosuspend.
- A client that follows a slider sends tens of writes a second. Each write used to rewrite the state file, and a UVC control write can take 5 to 50 ms.
- Strings that come from the device (control names, menu items) are untrusted text.
- The design must stay free of per-camera code ([../architecture.md](../architecture.md)).

## Decision
**The daemon describes a camera's settings as a tree of groups and typed settings, with the value, the range or options, and whether each can be changed now (and why not), all computed by the daemon. D-Bus revision 7 carries the tree in one snapshot method and a delta signal, the CLI carries it as a set of capped JSON lines, and the user's values are stored per camera and written whenever the camera opens, as in ADR-0020. The catalogue of known controls is data, the rules between controls are data, and any behaviour that belongs to one camera model is a data row keyed by its USB vendor and product ids.**

### The model
- A **setting** has an id `camera.<group>.<name>` (grammar `^[a-z0-9]+(\.[a-z0-9_]+){1,3}$`, at most 48 bytes), a label, a type (`bool`, `int`, `enum`, `action`), a scope (`camera`: the value is kept per camera id), and the keys of its type: a range, step, default and optional unit for an `int`; options (value id and label) for an `enum`; none for an `action`, which has no value. A widget hint (`slider`, `switch`, `segmented`) is a suggestion. The value, `stored` (the user has set one), `enabled` and `disabled_reason` are the state.
- Settings are in five **groups**, in this order: `image`, `white_balance`, `exposure`, `focus` (labelled "Focus & zoom") and `other`. A group with no setting is not published.
- `stored` and "different from the default" are two facts: a camera can be away from its default with nothing stored, and the per-row reset of a client keys on `stored`.
- **Which controls.** Every control of the user and camera classes whose type is integer, boolean, menu, integer menu or button, for every camera alike. Known ones are in a catalogue in the daemon, as data: group, label, unit, stable ids and labels for menu items, and the rule that makes a control depend on another. Any other goes to `other` with the device's own name, so a camera's extra controls appear without a code change. Never exposed: `privacy` and every relative, continuous (except the automatic-focus switch) or speed motion control, which are not settings but motion. A menu offers exactly the items the driver reports.
- **`enabled` is computed by the daemon**, never by a client: from the catalogue's rule over the *effective* values of the controls it depends on (the device's while the camera is open, the stored values, else the default after a pending reset, while it is closed), and from the device's flags (disabled, read-only, grabbed, and while open also inactive). A rule is also shipped as `enabled_when` conditions (`eq`, `ne`, `in`; AND-ed; a closed set) for display, but a client trusts `enabled` and evaluates nothing. The reason is a sentence for a person (`Set exposure to manual to change this`).
- A control the device marks **inactive stays in the tree, greyed with its reason**; revision 6 left it out of its list. A write to a setting that is not enabled is refused with `Disabled`, never stored.
- **The inverted toggle.** The V4L2 control `exposure_dynamic_framerate` lets the camera lower its frame rate in low light when it is on. It is published as `camera.exposure.keep_framerate`, "Keep 30 fps in low light", whose value is the opposite of the raw one. It is stored as the raw value under the control's name, so the state file does not depend on how a client shows it.

### D-Bus revision 7 (additive)
- Properties `SettingsRevision` (bumped at every change of the published tree) and `SettingsSchemaSerial` (bumped only at a structural change: another camera, a setting added or gone, a type, range, step, default, unit, options, conditions, hint or label changed), both from 1.
- `GetSettings(a{sv} options) -> (u revision, u serial, s camera, aa{sv} groups)`, `SetSetting(s id, v value, a{sv} options)` and `ResetSettings(s scope, a{sv} options)`, with `scope` one of `camera`, `group:<id>`, `setting:<id>`. `options.camera` names a camera (an id of `Cameras`; `ActiveCamera` when absent); on a write it guards against a switch of camera between drawing and clicking. With no camera, `GetSettings` is not an error: it replies no groups.
- Signal `SettingsChanged(u revision, u serial, a(sa{sv}) changes)`: one per controller operation, so a write and the dependency flip it causes are one signal. A change carries `value`, `stored`, `enabled` and `disabled_reason`. When the serial moved the list is empty and the client calls `GetSettings`.
- Errors: `UnknownSetting`, `Disabled` and `RateLimited`, besides the existing ones. The order of the checks on `SetSetting` is: the camera, `UnknownSetting`, `Disabled`, `InvalidArgument` (the wrong D-Bus type, outside the range or off the step, not an option), then, for a write to the device, the coalescing window and `RateLimited`.
- The revision-6 members (`CameraControls`, `GetCameraControls`, `SetCameraControl`, `ResetCameraControls`) stay with their types and meanings, as adapters over the same model and the same storage: they show and change the five image controls only (inactive ones left out, as before), and `ResetCameraControls` resets only those five. `InterfaceRevision` is 7. Details are in [../dbus-api.md](../dbus-api.md#camera-settings).
- The client follows the tree by the rules in the API reference: keep it while the serial stays, apply a delta of the next revision, read again on a serial change or a gap in the revision.

### Writes: coalescing, rate limit, write-behind
- **Coalesce, do not refuse.** At most one device write per setting every 50 ms. A valid `SetSetting` that arrives inside the window is *held*, reply included; a later one for the same setting replaces it and the superseded call is answered `Ok`; when the window opens the held value is validated again, written and its call answered with the real outcome. The last value always wins. A reset whose scope holds the setting drops the held write the same way. Held writes follow a rename of the session's camera, are only stored if the camera closes meanwhile, and are carried out at shutdown.
- **A global cap** of 100 device writes in any second: over it, `RateLimited`, and nothing is stored. Writes at an open and by resets are not counted.
- **Write-behind.** A settings change marks the state dirty and is saved once 300 ms have passed without another, and at once at shutdown, before a camera switch and with any other state change. While the state file is known not to take a write (damaged, or its last save failed) a change is saved, or refused, at once and returns `Failed` (the revision-6 behaviour); a delayed save that fails is logged and shown in `Error` when nothing else is. A crash loses at most the last 300 ms of changes; the device keeps its values anyway.

### Storage (extends ADR-0020)
- The same table per camera id, `[camera_controls."<id>"]`, now holds any control name (`^[a-z][a-z0-9_]{0,31}$`), as *raw device values*: `values = { sharpness = 128, field_of_view = 2, exposure_dynamic_framerate = 0 }`. A value the device does not take at an open is skipped and kept, as in ADR-0020.
- A pending reset is `reset_all = true` for the whole camera, or `reset_names = ["contrast", ...]` for a narrower scope and for the revision-6 `ResetCameraControls`. At the next open the defaults are written first, dependent settings first, then the stored values, masters first: a master has to be in place before the setting it enables.
- **Migration.** A revision-6 (0.21) state file has `reset_pending = true`, which meant the five image controls. It is read as those five names in `reset_names`, never as `reset_all` (which now means every control), and never written back.
- Writes at an open: masters (settings without a rule) first, then the camera is read again and the dependents follow; a stored dependent that is inactive at that moment is not written and stays stored, because its value would have no effect. Resets write dependents first, and skip a control that is inactive at that moment.

### Control events
- While the session has the camera open, the daemon holds one extra read-only descriptor on it, subscribed to `V4L2_EVENT_CTRL` for every published control, and waits for events on its own thread, with an eventfd to stop it. An event is a command to the controller; the camera is read again 50 ms after the first of a burst and the difference is published as one delta. An event that only reports what the last read already shows (the echo of the daemon's own write) is ignored. A watcher that cannot subscribe is logged once and the settings follow the other refresh points.
- The descriptor is held only while the camera is open and released when it closes or changes. A closed camera is left untouched and can autosuspend.
- This replaces the polling that ADR-0020 declined. Nothing is polled.

### A stored choice and the frame-rate pin
- `[camera] fixed_framerate` pins `exposure_dynamic_framerate` to 0 while a camera streams and restores it afterwards ([ADR-0009](0009-ingest-process-output.md)). The user's choice wins: a camera with a stored value for that control is not pinned, and its stored value is written at the open like any other. Without a stored value the configuration behaves as before.
- A reset while the camera is pinned writes 0, the pin, not the control's default, and forgets the stored value: the pin holds over a reset.

### Quirks as data: model-specific behaviour is a row, keyed by USB VID:PID
- **The rule.** Behaviour that belongs to one camera model is expressed as a data row keyed by the camera's USB vendor and product ids. It is never a branch in the model, the controller or a client, and the rest of the design stays model-independent. A row is offered only if the device agrees (its own query answers say it can be read and written). Adding a camera's setting means adding a row.
- **The row today: the Logitech field of view.** `obc_pipeline::xu::FIELD_OF_VIEW`, for `046d:0944` (MX Brio) and `046d:085e` (Brio): the Extension Unit's GUID `49e40215-f434-47fe-b158-0e885023e51b`, selector 5, a one-byte value, and the menu `90` ("90°", 0x00), `78` (0x01), `65` (0x02). It appears as `camera.focus.field_of_view`, an `enum`, and is stored as the raw byte under `field_of_view`.
- **Mechanism.** The node's USB device is found in sysfs by the node's device number (not its name), the rows are looked up by vendor and product, and the unit id of the row's GUID (it differs from camera to camera) is found in the descriptors of the device's *active* configuration, inside the VideoControl interface only: the same descriptor subtype inside a VideoStreaming interface is a format descriptor and must not match. Queries go through `UVCIOC_CTRL_QUERY`, which needs no privilege beyond access to the node.
- **Safeguards.** The queries are held to an allowlist: only `SET_CUR`, `GET_CUR`, `GET_LEN`, `GET_INFO` and `GET_DEF`, only on a row's own unit and selector, and a write only of a value in the row's menu. No other unit or selector can be reached through that module. The row is offered only if `GET_LEN` equals its size and `GET_INFO` says read and write. The setting is written only while the camera is open. The capture format is read before and after the write; if it changed, the previous byte is written back and the call fails (`Failed`, `changing the field of view changed the camera's format`). A current byte that is not in the menu shows the setting greyed (`The camera reports a field of view this version does not know`) and is never overwritten by a test or a default.
- **Evidence.** On the MX Brio the unit is 10 (of 8 Extension Units), the byte reads 0x02 (65°) with `GET_DEF` 0x00 (90°) and `GET_INFO` 0x03, and switching between 78° and 65° while the camera streams 1920x1080 NV12 at 60 frames per second left the capture format and a consumer's caps unchanged. Whether the camera keeps the value across a power cycle has not been established; the daemon writes the stored value at every open, so it does not depend on it.
- **Not exposed, on purpose.** The camera's LED sits in another unit, and the kernel blocks it as a privacy control (`uvcvideo` answers `EACCES` unless a root-only module parameter overrides it, which was confirmed on the camera); no code bypasses that, and the allowlist cannot reach it. HDR and RightLight are not pursued: no byte sequence for the MX Brio is known, and sending unknown payloads to the vendor units, one of which also holds a save-to-memory command on related cameras, is not acceptable without a verified source.

### The CLI and the JSON lines
- `omarchy-broadcast settings [--json] [--camera=ID]` reads without starting the daemon; `settings set [--camera=ID] [--] ID VALUE` and `settings reset [--camera=ID] [--group=GID | --setting=ID]` may start it, like the other setters. `set` reads the tree to type the value (`on`/`off`, a whole number, an option id, nothing for an action), then prints the setting read back and whether it applied live or applies at the next open. Exit codes are as before; `Disabled`, `UnknownSetting` and `RateLimited` are exit 1 with the daemon's message.
- `watch --json` prints, after the `snapshot`, the full set of the active camera as `settings_group` lines, then a `settings_delta` per `SettingsChanged`, a new set on a serial change or a gap in the revision, and a `settings_clear` line when there is nothing to show. The snapshot gains `settings_revision` and `settings_schema` (`null` below revision 7). **`v` stays 1**: new fields, new line types and a new command are not breaking ([../cli-json.md](../cli-json.md#versioning)).
- **Chunking keeps the cap.** A set is cut into lines by group, a group over several lines when it does not fit, at most 8 settings a line, packed greedily by encoded length. Bounds on every string and list (label 48 bytes, reason 96, unit 16, option value and label 32, 16 options, 4 conditions, 8 operands) make one setting at its bounds fit a line alone. A client assembles a set by `rev`, `serial`, `index` and `count`, commits it when it is whole, applies deltas of the committed serial and revision, and treats `settings_clear` as nothing to show.
- **The settings schema version** (`schema`, now 1) is the version of the meaning of a setting object, separate from `v` and from `InterfaceRevision`. Additive changes (a key, a setting type, a hint, a group) keep it: clients ignore unknown keys and skip a setting of an unknown type, never failing. A change of meaning an old client would misread raises it, and a client that meets a higher schema than it knows shows no settings and asks for an update.
- Tests: [../testing.md](../testing.md#camera-settings).

## Consequences
- Revision 7 is additive: a client built for revision 6 keeps working and sees the five controls through the old members; a revision-7 client against an older daemon sees no `settings_schema` and shows nothing.
- A client has no list of controls and no rule evaluator. A new camera, a new catalogue entry or a new row appears in the clients without a change to them. Clients draw by type and show the reason.
- Controls other than the five reach the user's camera through the same path as ADR-0020: stored per camera, written at each open, never to a closed camera. A user who sets a value changes the camera for every application, as before, and the whole-camera reset puts every control back.
- A setting that the camera makes inactive is visible and explained instead of missing, and a write to it fails with a message that says what to change first. Two calls are needed to change a dependent setting from a closed state (the master, then the dependent), and both are stored.
- A value changed by other software or by the camera shows within a short moment while the camera is open, with no polling. The cost is one extra descriptor on the node while it is open, and one thread.
- The user's stored "Keep 30 fps in low light" overrides the configuration's pin for that camera.
- Known limitations:
  - **The pin's restore at close.** A change of `keep_framerate` while the camera is open *and pinned* is written, stored and logged, but the ingest's guard, which the daemon has no way to disarm, restores the value it found when that session closes; the stored choice applies again at the next open.
  - **The event watcher exists only while the camera is open.** A change made by other software to a closed camera shows at the next refresh point (a rescan, an open, the first frame, a read of the tree), not at once. A camera whose driver does not deliver control events is followed at the refresh points only.
  - A driver may round a written value; the value read back is what the tree shows.
  - A held write's reply takes up to 50 ms, and the caller of a superseded write cannot tell that its value was replaced (it is answered `Ok`). The 100-writes-a-second cap is global to the daemon, not per client.
  - A camera with more than 64 controls, or a menu with more than 16 items, loses the rest, logged once.
  - Only camera settings are in the tree. The video effects, noise removal and the preview stay separate properties and methods; the `scope` key leaves room for settings that are not per camera. The tree is of `ActiveCamera`; another camera's tree is read with `GetSettings` and has no signal.
  - The state file keeps an entry for a camera that is no longer plugged in, as in ADR-0020, and a stored value for a control a different firmware lacks is skipped and kept.
  - `enabled_when` is a hint: a client that does not understand a condition has `enabled` anyway.
  - The settings revision is a 32-bit counter; a client that sees it wrap treats it as a gap and reads the tree again.
  - A worst-case `snapshot` line now holds 11 of the 12 cameras the bound allows (the two new fields take the room of one at the string bounds); realistic ids fit all twelve.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| The tree as JSON in one string property | A property is sent whole with every `PropertiesChanged`, so every slider tick would resend the entire tree; the type system tells nothing about a blob, and there is no batching or bound on the size of a change. Typed `a{sv}` with a snapshot method and a delta signal keeps the extensibility (a new key, ignored by old clients) and adds introspection and bounded signals |
| One D-Bus object per setting (ObjectManager and Properties) | The best fit for `busctl tree`, but a camera switch would be 17 `InterfacesRemoved` and 17 `InterfacesAdded`, a dependency flip would be N separate `PropertiesChanged` with torn reads in between, and the daemon needs dynamic object registration with lifetime races. The plugin never sees D-Bus (it uses the CLI), so the gain would go to a client that does not exist. A read-only facade on the same model can be added later |
| Raising the 4096-byte line cap (`v` 2) | A breaking change to a documented rule, for every client, to avoid chunking. A set cut by group, with `index`/`count` and packing by length, keeps `v` 1 and the guarantee |
| Keep hiding inactive controls, as revision 6 does | A client cannot show a greyed control with its reason, and a user cannot discover that exposure time exists behind the automatic mode. Greyed with a reason costs the daemon one more flag |
| Accept a write to a disabled setting and store it for later | The camera ignores the value while the control is inactive, and a later open would then apply a value that the user chose when it did nothing, with the master possibly changed meanwhile. A refusal with the reason (`Disabled`) is honest and costs one more call |
| A client-side evaluator for the rules | Puts an expression language in every client (QML included) and lets clients disagree. `enabled` is computed by the daemon, which also sees the device flags; `enabled_when` is only a hint for display |
| Poll the device to follow changes | Touches the device at intervals, also when the daemon is otherwise idle. V4L2 control events deliver exactly the changes, with no poll |
| Subscribe to control events also while the camera is closed | An open descriptor keeps a UVC camera out of autosuspend, and ADR-0006 and ADR-0020 leave a closed camera untouched |
| A bidirectional `session --json` command (one child for both directions) now | It would save a process per write, and the plugin builds JSON without a shell. It also needs a stdin line reader with its own cap and a write queue in the client. A fork per write was acceptable, and the channel can be added later without changing the tree |
| Branches in the model for a camera model | Per-model behaviour in code spreads. A data row keyed by VID:PID keeps the model, the controller and the clients free of it |
| Expose the Extension Unit through the kernel's control mapping (`UVCIOC_CTRL_MAP`) so that it looks like a V4L2 control | Deprecated in the kernel ("will eventually be removed"), and not needed: the query ioctl is enough |
| Expose the camera's LED | The kernel blocks it as a privacy control, and bypassing a privacy guard is not this daemon's job |
| Expose HDR or RightLight with payloads from a related camera | The byte sequences are unverified for the MX Brio, and the same unit has a save-to-memory command on related cameras |
| Leave out `exposure_dynamic_framerate`, or show it as "managed by the daemon", read-only | The user's choice is a legitimate one for a camera that is not used for a call, and "Keep 30 fps in low light" is the form a person understands. The stored choice wins over the pin instead |
| Store values by setting id | The control's name is what revision 6 stored, raw values keep the inverted toggle independent of how a client shows it, and a state file written by 0.21 stays readable |
| Reject a burst of writes (rate limit alone) | A slider is a legitimate stream of values and only the last one matters. Coalescing answers every call and writes the last value; the cap is a backstop |

## What would change this decision
- A client that wants per-setting objects (`busctl tree`, other tools): a read-only facade on the same model, not a second model.
- Slider traffic where a fork per write shows in practice: the bidirectional session command, additive to the tree and the lines.
- Settings that are not per camera (the effect choice, noise removal): new `scope` values and settings in the same tree, with the existing properties kept; additive unless the meaning of a key changes.
- A change in meaning of a key or an `enabled_when` operator: the settings schema becomes 2, and clients that do not know it say so.
- A verified way to change HDR, RightLight or another vendor setting: a data row in the same table, with its own evidence.
- Control events proving unreliable on a camera that matters: a refresh on a timer while open, as an option, not the default.
- Evidence that users want writes to disabled settings kept for later: a stored value flagged as waiting for its master could be added, with its own display.
