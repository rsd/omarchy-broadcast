# ADR-0025: Loadable modules: effects as a manifest and a shared library behind a versioned C ABI

- **Status:** Accepted (2026-11-10), implemented as phase 1 of the module system: daemon 0.24.0, D-Bus revision 9. Extends [ADR-0012](0012-video-effects-and-maxine-backend.md) (the `InferenceBackend` seam becomes one of the things a module implements; the Maxine backend moves into a module), [ADR-0024](0024-stackable-stages-and-effects-in-the-settings-schema.md) (stage ids become strings and a module declares its own) and [ADR-0023](0023-settings-schema.md) (the global settings are described by the modules installed). Amends [ADR-0012](0012-video-effects-and-maxine-backend.md) and [ADR-0024](0024-stackable-stages-and-effects-in-the-settings-schema.md) where they describe the process-wide SDK root and the closed `Stage` enum (see the notes in those records). Keeps [ADR-0003](0003-maxine-first-behind-backend-seam.md): the SDK is never vendored. Author guide: [../modules.md](../modules.md). Amended by [ADR-0026](0026-config-d-and-managed-config.md) (phase 2): the module choices described under "Runtime choices live in the state file" are kept in `config.d/50-panel.toml`, not in the state file.

> *Amended by [ADR-0029](0029-audio-modules-mic-host-and-worker.md): the `audio-filter` kind is no longer reserved. It has an ABI of its own (1.2, additive), and its modules are loaded in-process by a host of their own, the audio worker, never by the daemon; the daemon lists them without opening their libraries. "In-process only" below holds for each host. The text below is the original decision.*

> *Amended (2026-11-12, D-Bus revision 14): the module-level `conflicts` and `[requires] modules`, the stage `conflicts` and `requires` are enforced, a debugging override exists, and a requested background effect never shows the raw camera. See "Update: conflicts, requirements and the override" at the end.*

## Context
- Up to revision 8 the effects were an NVIDIA feature of the daemon. The stages were a closed enum (`Stage { Denoise, Relight }` with a fixed canonical order), the SDK's features a closed list, the backend a hard-coded default (`EffectBackend::default()` was Maxine, as was the enhance stage's), the effect settings a compile-time table in the daemon, and the SDK root a process-wide value in the pipeline crate. The seam was GPU-only: `DeviceNv12` held `CUdeviceptr` planes and `GpuContext` a `CUcontext` and a `CUstream`.
- Most machines have no RTX GPU, and the project should be distributable, and open to contributions, without a change to its core. Effects and filters are meant to be installed as needed and stacked in an order the user picks, and the hardware they run on (NVIDIA through Maxine today; a CPU or ONNX Runtime backend, OpenVINO, AMD from contributors later) is meant to be replaceable per effect. ADR-0024 ("Extensibility") listed what blocked this.
- A module can be proprietary or under a licence that does not fit this repository (the Maxine SDK is NVIDIA's). The daemon must be able to load code that is built and distributed separately, without that code, or its licence, entering the daemon's source or its binary.
- A module can be broken: a missing library, another interface version, a crash. The daemon, and the camera that applications hold open, must survive that, as far as a process can ([ADR-0022](0022-crash-recovery-for-consumers.md)).
- The daemon must not wake a runtime-suspended GPU to find out what is installed ([ADR-0006](0006-on-demand-gpu-lifecycle.md), [ADR-0017](0017-cuda-checkpoint-parking.md)).
- Clients (the CLI, the bar plugin) carry no list of effects: they draw the settings tree ([ADR-0023](0023-settings-schema.md), [ADR-0024](0024-stackable-stages-and-effects-in-the-settings-schema.md)). A module has to bring its own settings to it.
- D-Bus policy ([ADR-0005](0005-dbus-zbus-control-plane.md), [../dbus-api.md](../dbus-api.md#versioning)): additive changes stay on `…OmarchyBroadcast1` and raise the revision.

## Decision
**An effect is provided by a module: a TOML manifest in a `modules.d` directory and a shared library that exports a versioned C ABI. The daemon finds modules by reading manifests, opens a library only for a module that is enabled, runs it in-process, and lets it describe its stages and its settings. The core knows two stage ids, `background` and `enhance`, and the rest is opaque to it. With no module the daemon passes the camera image through.**

### A module is a manifest and a library
- **Manifest** (`<name>.toml`, any name, in a `modules.d` directory): the module's reverse-DNS id, name, version, licence, `kind`, `library` (absolute, or relative to the manifest's directory), `abi` (the ABI major version it was built for) and one `[[stage]]` per stage it provides. A stage declares its `id`, `slot`, `rank`, `device`, `position`, `requires`, `conflicts`, the frame kinds (`frames`) and pixel formats (`formats`) it accepts. Unknown keys are refused, so that a typo makes the module unavailable with the parse error as its reason, rather than being ignored. The reference is [../modules.md](../modules.md#the-manifest).
- **Discovery reads manifests and nothing else.** The directories are, in order, `/usr/lib/omarchy-broadcast/modules.d`, `$XDG_DATA_HOME/omarchy-broadcast/modules.d` (default `~/.local/share/...`), the configuration's `[modules] dirs`, and the colon-separated `OBC_MODULE_PATH`; a later directory overrides an earlier one by module id, so a user install replaces the packaged one. No library is opened at discovery, so a broken one cannot stop the daemon from starting. A library is opened when its module is enabled, then checked (below) and probed.
- **The ABI is C**, in the crate `obc-module-abi`: `#[repr(C)]` types and constants, and the header `include/omarchy_broadcast_module.h`, generated from them by cbindgen and committed (a test regenerates it and fails on any difference; another compiles it as C and as C++ against the Rust layouts). A library exports two symbols: `obc_module_abi_version`, side-effect free, and `obc_module_entry`, which takes the host's description and returns a vtable. The Rust SDK `obc-module-sdk` wraps the ABI in a safe API (`Module`, `Instance`, the `export_module!` macro; it catches panics at the boundary), and a module in another language implements the header directly. `examples/module-hello`, outside the workspace and built on its own, shows an out-of-tree module.
- **Version policy.** The host calls `obc_module_abi_version` before anything else of the library and refuses a different **major** version, and a **minor** version newer than its own, each with a reason that names both versions; the entry point is not called then. A module built for an older minor version of the same major version loads. A structure that can grow starts with `struct_size`, fields and vtable entries are only appended, and a reader reads a field only when it fits in `struct_size` (a vtable at least as large as that of ABI 1.0 is accepted, and an entry past its `struct_size` counts as not set). A manifest whose `abi` is not the host's major version is listed with the same reason and its library is never opened. **ABI 1.x is not yet declared stable:** until it is, it may change in breaking ways, and a module built outside this repository may need rebuilding against the matching SDK or header after an update of omarchy-broadcast. No module outside this repository exists yet, and what a promise of stability should be ("a major bump is a break" from the first release, or unstable until the first external module is released and frozen per major version from then on) is an open question.
- **Failure of a module is its status.** A broken manifest, a missing library, another ABI version, a failing `init`, probe or `check`, a manifest kind that is not supported yet, each becomes the module's `status` (`unavailable`, with a reason) and the daemon runs on. A panic in a module written with the SDK is caught and returned as the failure of that call. What cannot be contained is a crash of native code, which takes the daemon down; see the crash ledger below.
- *Amendment (daemon 0.41.0, D-Bus revision 16): the ABI is 1.3, which adds one nullable vtable entry, `instance_status_values`, and the structure `obc_status_value` (stage id, name, an `f64` value; 32 bytes). A stage reports named numeric values about the last processed frame, which the daemon publishes as the read-only `StageValues` property (`a(ssd)`) and the CLI prints (auto-frame's zoom is the first). The reasons: the daemon's status could show only what the host itself measured (the step times of `instance_timings`), while a value such as the crop an auto-framing stage has chosen exists only inside the module, and a panel that offers the setting has nothing to show the user of what it does. The entry is **pulled after a frame**, like `instance_timings`, not pushed: the module does no work of its own to report, the host reads on the streaming thread and under the element's existing non-blocking lock (a frame whose lock is not taken leaves the last values), and a module with no values leaves the entry null. It is additive under the version policy above: a 1.0 to 1.2 module has a shorter vtable, which the host counts as not set; a 1.3 module on a 1.2 host is refused by the minor check. The host trusts nothing it reads: at most 64 entries (a longer list is ignored whole), a null, misaligned or non-OK answer gives none, names are cut to 64 bytes, and an empty name, an invalid stage id or a value that is not finite is dropped, because the list crosses a C boundary from a library the daemon cannot vouch for, and the same bounds now apply to the timings. A value is kept only for a stage that is ready and ran on the last frame, so a stage switched off or failed shows nothing stale. On the bus the property is announced when the set changes or a value moves by 0.01 or more, at most every 250 ms: auto-frame's zoom eases continuously, and announcing every frame would flood `PropertiesChanged` for a figure that a person reads to two decimals. The values are read-outs and not settings, and nothing writes them. See [modules.md](../modules.md#status-values-abi-13) and [dbus-api.md](../dbus-api.md#stage-values-revision-16).*

### In-process only
- Modules run inside the daemon, through the ABI. The ABI carries no Rust types and passes frames as described handles, so that a host that runs a module in another process could wrap the same ABI later; none is built.
- The accepted cost: a module that crashes takes the daemon down. The recovery of ADR-0022 (the unit's restart, the loopback's timeout frames) applies, and the **crash ledger** keeps a module from doing it repeatedly. The ledger is a JSON file, `modules-crash.json`, in the state directory. A marker for a module is set while its code runs a pipeline or a probe and cleared on a clean stop. At start, a module whose marker is found counts one strike, a start that finds none resets the count, and at **two strikes in a row** the module is disabled, with the reason "Disabled after crashing the daemon twice in a row", until the user enables it again (`SetModuleEnabled`, which clears its strikes). A session marks only the modules whose code actually runs: the effect module when the background effect is on or one of its stages is requested, the enhancer when enhancement is on, and another module's chain when one of its stages is.

### Frames, kinds and conversion
- A frame is a described handle: kind, pixel format, size, planes (a pointer or descriptor, a pitch, an offset), the CUDA context and stream for device memory, a timestamp and flags. The kinds are `cuda` (a device pointer in the stream's shared CUDA context, as in ADR-0012) and `host` (memory the module may read, and write for an output frame, during the call). **`dmabuf` is reserved**: it has a number in the ABI and an entry in the manifest's vocabulary, and no host offers it.
- Each stage declares the kinds and formats it accepts. The host converts **only at module boundaries**: a chain inside one module stays in the memory it was loaded for. A chain that takes only `host` frames, offered CUDA frames, runs through a page-locked host copy (download, process, upload back into the same frame, on the element's own stream); a chain that takes only `cuda` frames cannot run on system memory, and its stages fail with the reason.
- For `cuda` frames the host makes the stream's CUDA context current around every call, and a module never creates a context of its own, or makes one current. This is the rule of ADR-0012, now stated at the ABI.

### Stage ids, slots and a constrained order
- A **stage id** is a vendor-neutral string, `^[a-z][a-z0-9-]{0,31}$`, other than `status`, `effect`, `reason`, `module` and any name ending in `-reason` (they are the field names of the elements' status messages). `background` (the cut-out and the core compositor's modes `none`, `blur` and `replace`) and `enhance` (the ingest's upscaler) have a meaning to the core; every other id (`denoise`, `relight`, `hello`, ...) is opaque to it.
- A stage declares a **slot**, in pipeline order: `pre-matte` (on the camera frame, before the cut-out), `matte` (the cut-out), `post-matte` (on the person, after the cut-out) and `post-composite` (on the composited frame). It may declare `requires` (stage ids, or slot names: `matte` is satisfied by any earlier stage of that slot) and `conflicts`, and a `position` that orders it within its slot.
- The **stage order** is one total order over every stage the enabled modules offer, available or not. It is valid when the slots never go back and every `requires` entry that some enabled module offers is met by a stage earlier in the order. The default order is by slot, then `position` (default 100), then stage id. The user may set another order within those limits (`SetStageOrder`); the daemon refuses an invalid one with the reason, and replaces a stored order that no longer fits the modules found by the default, with a warning. A set that leaves a stage out, names one twice or names one that is not offered is refused. An empty list sets the default.
- `conflicts` is read and kept, and the host library can evaluate it, but phase 1 does not turn it into a refusal or a greyed setting.

### Which module provides a stage: rank, pin and profile
- Each stage declares a `rank` (higher is better) and a `device` (`nvidia-gpu`, `gpu`, `npu`, `cpu`). The **provider** of a stage is chosen among the enabled, available modules whose stage is available: the module the user **pinned** (`SetStagePin`) when it can run the stage; else by the **profile**: `quality` takes the highest rank, `battery` prefers the device (an NPU, then the CPU, then a GPU, then an NVIDIA GPU) and then the rank. Ties go to the lower module id. A pin that cannot be honoured falls back to the profile and the stage says why ("Pinned module ... is unavailable: ...").
- The choice is made **when a pipeline starts and never changes while it runs**. A failure of the provider falls back only as the failure rules below say, and a stage is never silently handed to another backend in mid-session. A change of profile, pin, order or of the enabled modules is stored at once and applies when the camera next starts. *Amendment (D-Bus interface revision 11): no backend is handed over mid-session still, but a session follows what its modules provide: a stage whose module is disabled (or can no longer run it) is turned off in the running session, and turned on again when the module can run it again; and a selected stage (the background effect, another stage, enhancement) that the session has no module able to run, once a module provides it, restarts the session once (a new pipeline with a new plan, from black frames as at any start) rather than waiting for the next start. A profile, pin or order change alone still applies at the next start: a stage whose module in the session can still run it stays there.*

### Registry-driven settings
- A module describes its settings as JSON (`describe_settings`), in the self-describing model of ADR-0023 (types `bool`, `int`, `enum`, `action`; ids `effect.<group>.<name>`; the limits on counts and lengths unchanged). A setting binds to a stage: `role: "enable"` marks the stage's on/off switch, `key` binds a parameter, and `apply` says whether a change applies per frame (`live`), reloads the chain (`reload`, the default for a bound key) or waits for the next start (`restart`). A setting that is malformed or breaks a rule is dropped with a log line, and the module and its other settings stay.
- The daemon's settings model is built from what the enabled modules describe, in module id order, after the camera's groups. **The `background` group is the core's**: `effect.background.mode` (`none`, `blur`, `replace`) and `effect.background.blur_strength` belong to the compositor, which is core code, and the group is shown only while an enabled module provides the `background` stage (or a mode other than `none` is in force, so that it can be turned off). A module group with that id is dropped.
- Values persist by setting id in the state file (`[settings]`); the typed revision-8 keys (`denoise`, `enhance`, `relight`, `relight_light`, `relight_direction`, `relight_brightness`) are still read, and still written next to it, so that a daemon of revision 8 reading the same file keeps those choices. A module's own configuration is a free table, `[module."<id>"]`, passed to it as JSON at `init` and checked by the module; the daemon checks only the id. The reference rev-8 behaviour is kept exactly for Maxine: its module describes the rev-8 ids, labels, ranges, defaults and reasons.

### Maxine is a module and owns its SDK root
- `crates/obc-module-maxine` builds `libobc_module_maxine.so` (with the manifest `maxine-vfx.toml`) from the Maxine backend of `obc-backend-maxine`. The daemon and the pipeline crate link no Maxine code and no SDK, CUDA or TensorRT library; the module opens the SDK at run time, when a chain loads, so that the library loads on a machine with none of them. Its stages are `enhance` (pre-matte, position 0), `denoise` (pre-matte), `background` (matte) and `relight` (post-matte, requires the matte).
- **The SDK root is the module's.** Its configuration key is `sdk_root` in `[module."br.com.dias.maxine-vfx"]`. `[effect] maxine_root` is still honoured as an alias, passed as `sdk_root` when the module's table sets none, and `MAXINE_VFX_ROOT` still wins over both ([ADR-0021](0021-nvidia-sdk-handover.md)). The process-wide `set_maxine_root`, the root-conflict check of the pipeline crate and the `Feature` list of the SDK are gone from the daemon and the pipeline: what is installed is the module's probe, which reads the SDK's files and nothing else (no `dlopen`, no CUDA), as in ADR-0024. The daemon keeps the module's id, for the `maxine_root` alias, and the compute-capability cache, which it hands to every module as the `_host` key of its configuration. The pin of the loaded root (one SDK per process, for its life) is in the module's library, which is why a library is never unloaded (below).
- A deeper check, `check`, is a nullable entry of the vtable that the host runs before a stream that needs the module starts. It may open the module's own runtime libraries and must not create a CUDA context or touch the GPU. The Maxine module uses it for what the built-in backend did before the camera opened: telling that the SDK cannot be loaded.

### Zero modules, and the rev-8 aliases
- With no module installed (or none enabled) the daemon starts and the output passes the camera image through; the settings tree has no effect group, the CLI says "No effect modules installed", and a request for `blur` or `replace` fails like any effect that cannot load ("effect blur unavailable: no effect module provides the background effect ...", closed by default). *Amendment (D-Bus interface revision 14: the background effect now follows `on_failure` here, see the update at the end; the text of this amendment holds for every other stage.)* *Amendment (D-Bus interface revision 11): such a request is kept and the stage dropped instead: the output passes the camera image through (with the stages other modules provide), the state is `active` as usual, and the reason is in the `Warning` property, not `Error`; `effect.on_failure` applies only to a provider that exists and fails, and from the same revision never stops the stream (`black` streams black frames with the reason in `Warning`). The same holds when the module is disabled during a session: its stages leave the running stream at once, and enabling it again brings them back (restarting the session once when it was started without the module and one of its stages is selected).*
- D-Bus revision 9 is additive ([../dbus-api.md](../dbus-api.md#modules)): `GetModules`, `SetModuleEnabled`, `GetStageOrder`, `SetStageOrder`, `SetBackendProfile`, `SetStagePin` and the properties `ModulesSerial` and `BackendProfile`. Every revision-8 member keeps its type and meaning: `SetEffect`, `SetBlurStrength`, `SetDenoise`, `SetBackgroundImage`, `Effect`, `BlurStrength`, `Denoise` and `BackgroundImage` map onto `effect.background.*` and `effect.video.denoise`, and the CLI's `effect` and `denoise` commands stay. The CLI gains `modules` and `order` ([../cli-json.md](../cli-json.md#modules-and-order)), with the JSON line types `modules`, `module` and `order`; `v` stays 1.

### Decisions of phase 1
- **`EffectKind` stays.** `none`, `blur` and `replace` are the core compositor's mode of the `background` stage, not a list of modules. `obc-core::EffectMode` stays for configuration compatibility. A matte provider supplies the cut-out; the blur and the replacement are core.
- **Noise removal stays before the cut-out.** The Maxine manifest puts `denoise` in `pre-matte`. A `post-composite` slot, which is where a stage that works on the finished picture belongs, would have changed the rev-8 output (noise removal runs before the mask today, so the mask and the blur see the cleaned frame).
- **The ABI unit is an instance that loads an ordered chain of one module's stages.** `instance_load` takes the stage ids in order with the frame geometry, the colour description, the CUDA handles and the load-time parameters; `instance_process` takes one frame and the per-frame parameters; `instance_reset_temporal`, `instance_unload`, `instance_timings` and the park hooks complete it. A load on a loaded instance is a **switch** when the frames of the request are those of the loaded chain (only the stages, the parameters or the background change) and may reuse the models of the previous load; with other frames it is a reload.
- **Placement.** The provider of `background` hosts the whole matte family, its own stages that sit in `pre-matte`, `matte` and `post-matte`, inside the effect element (`obceffect`), as the Maxine chain ran before. Every other module's stages run in `obcmodule` elements, one chain per module and side: the stages in `pre-matte` before the effect element, the others after it. A stage that needs the cut-out (`requires` the `matte` slot or the `background` stage) but is provided by a module other than the `background` provider is unavailable ("Needs the cut-out of the module that provides it"): mixing modules inside one matte chain needs a shared compositor, which comes later. With Maxine as the only effect module this never applies.
- **Failure rules.** A failed switch that keeps the frame geometry leaves the previous chain loaded and running; a failed first load, a failed load at another geometry and a panic leave the instance unloaded (and the host unloads it). The matte never fails open: a failure of the `background` stage, or of any stage of the `matte` slot, fails the whole chain and the effect follows `[effect] on_failure`, as in ADR-0012. A stage of any other slot fails open, as ADR-0024 says: it is dropped alone (`OBC_ERR_STAGE`, which names the stage), the others run on, and a frame it failed on runs again without it. In an `obcmodule` element a frame is processed in place, so before a chain or a stage runs again the element restores the input (a copy per frame while a stage is active: device to device on CUDA, a memory copy on system memory, a second download through the host copy); a chain that fails as a whole outputs the untouched input.
- **A library is opened with `RTLD_NODELETE`, so a rebuilt library needs a daemon restart.** A module may keep process-wide state that must outlive a reload (the Maxine module guards the SDK it loaded, which cannot be unloaded and loaded again from another place), and threads or callbacks it left behind must never run in unmapped code. The consequence is that a library rebuilt at the same path is not loaded again while the daemon runs: the code first loaded stays. A reload (`SIGHUP`, `ReloadConfig`) finds modules again, and keeps one open, and probes it again, when its manifest, its library file (device, inode, size, time) and its configuration are unchanged. A new or changed manifest, or a library at another path, is picked up on reload; a rebuilt library takes `systemctl --user restart omarchy-broadcastd`.
- **Runtime choices live in the state file.** Which modules are enabled, the order, the profile and the pins are in the state file's `[modules]` table, over the configuration's `[modules]` (`dirs`, `disabled`, `order`, `profile`, `pin`). The state file is the only place the daemon writes them: it never writes `config.toml`, and this phase adds no managed drop-in of the configuration.

## Consequences
- The daemon contains no vendor code. Maxine builds and installs as a module, the SDK is loaded when a stage loads, and the workspace builds and its default tests pass without the SDK.
- A third party can add an effect, or a backend for an existing one, without a change to the core, under its own licence, by installing a manifest and a library. The settings tree and the clients show its settings with no change.
- With two modules that provide a stage, the choice is the user's (profile and pins) and is stable for a session. The module list says which module provides each stage at the next start, and why a stage is unavailable.
- A module is trusted code in the daemon's address space: a native crash takes the daemon down, a module can read the process's memory and files, and installing one is a consent to that. There is no signing and no sandbox. The crash ledger bounds the damage of a module that crashes on every start.
- The behaviour of the revision-8 daemon with Maxine is preserved, with these differences: an SDK that cannot be loaded is found for the effect by the module's `check`, before the camera opens, as before, and for enhancement, which had no such check, when its first frame loads; every reload finds and probes the modules again, which costs a probe each, mitigated by keeping a module that did not change open.
- Stage ids are one namespace. Two modules that declare the same stage id are two providers of it; a module that declares a new id appears in the order and brings its own settings.
- `conflicts` is declarative only in this phase. *Amended: enforced from D-Bus revision 14, see the update at the end.*
- The `obcmodule` element copies a frame per output frame while one of its stages is active, to restore it when a stage fails halfway.
- Known limitations:
  - A stage cannot yet use the cut-out of a module other than the `background` provider.
  - Only `video-stage` modules load. The manifest `kind` also accepts `audio-filter` and `analyser`, which are listed as unavailable ("not supported yet"): the microphone stays on the PipeWire filter-chain ([ADR-0014](0014-mic-noise-removal-filter-chain.md)). *Amended by [ADR-0029](0029-audio-modules-mic-host-and-worker.md): `audio-filter` is implemented and loaded by the audio worker; only `analyser` remains reserved.*
  - `ModulesSerial` starts at 1 when the daemon has made its first list, so a client reads `GetModules` at connect and does not wait for a change.
  - A library rebuilt in place is not loaded again without a restart (above).

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| GStreamer plugins as the module system | Per-element schemas, no notion of a stage, a slot, a backend choice or a probe, and GObject boilerplate for every contributor. GStreamer stays the data plane, and the daemon's elements are the hosts of the modules' stages |
| `abi_stable` (a Rust-only stable ABI crate) | Ties every module to Rust and to the crate's type system, and is heavy for what crosses the boundary. A plain C ABI is smaller, can be written in any language, and is what a host that runs a module out of process would wrap |
| WebAssembly modules | No access to GPU or NPU memory, so a copy of every frame in and out; it also leaves the vendor SDKs that are the point of most backends out of reach |
| Compile-time cargo features | A module is then part of one build and one licence; it cannot be installed separately or kept out of the repository |
| Out-of-process modules now | A frame-transfer protocol, supervision and a second lifecycle for every module, with no need yet: the cost is complexity and delay, and the crash ledger covers the failure mode. The ABI is shaped so that it can be added |
| A breaking `…OmarchyBroadcast2` interface | Nothing requires it. Every revision-8 member keeps its meaning and the new ones are additive, per the versioning rule |
| Free-form stage ordering | Some orders cannot work (a stage that consumes the cut-out before there is one). Slots and `requires` make every accepted order runnable, and give a default and a reason when one is refused |
| Keeping `DeviceNv12` and `GpuContext` as the seam | They hold CUDA handles, which blocks every backend that does not run on CUDA. They remain as the `cuda` frame kind of the new seam, next to `host` |
| Discovering modules by opening their libraries | A broken library, or one that crashes at load, could stop the daemon from starting, and a probe of every library would wake what the daemon must not wake. The manifest says what a module offers; the library is opened for an enabled module only |
| One ABI object per stage (`create_stage`) | The unit that mirrors the existing seam is a chain: load, switch, process, reset and unload act on an ordered list of stages, the Maxine chain keeps its intermediate images on the GPU, and a switch reuses models. A chain of one stage is the degenerate case |
| Dropping `EffectKind` for a list of modules | The blur and the replacement are the compositor, which is core code so that every cut-out provider gets the same result. The mode stays a typed value of the `background` stage |
| Maxine's `denoise` in `post-composite` | Changes the output of revision 8, where the mask and the effect see the cleaned frame |
| Unloading libraries on reload | A module's process-wide state (the loaded SDK) and threads it left behind would be lost or run in unmapped code; the price of keeping libraries is a restart to load a rebuilt one |
| Hot-loading: changing the enabled modules, the order or a pin under a running pipeline | A session's modules, and the memory and contexts they hold, are fixed when it starts; switching a backend mid-session could show a frame the user asked to hide. The choice applies at the next start |

## What would change this decision
- A module that cannot be trusted in the daemon's process, or crash isolation that matters in practice: an out-of-process host that wraps the same ABI.
- The first module written outside this repository: the ABI is declared stable and the stability promise is stated (for 1.x, or for a 2.0 that is made), so that such a module does not need rebuilding after each update.
- A second cut-out provider: the compositor becomes a shared component that takes any matte, so that stages can mix modules in one matte chain, and the placement rule of this phase is lifted.
- A backend that produces or consumes DMA-BUF frames (VA-API decode, OpenVINO): the `dmabuf` kind is offered by the host and the conversion rules get a third case.
- Audio modules (microphone effects, captions): the reserved manifest kinds get an ABI of their own.
- Evidence that a rebuilt library should load without a restart: a module-level reload entry, or a per-load copy of the library, in place of `RTLD_NODELETE` for the modules that opt in.

## Update: conflicts, requirements and the override (2026-11-12, D-Bus revision 14)

Phase 1 read `conflicts` and a stage's `requires` but acted on neither. Revision 14 enforces them, and with them reaches a case the earlier rules did not have to face: a module refused for a reason of its own, which can be the module that hides the room.

**What is enforced.**
- A module's `conflicts = ["<id>"]`: an enabled module that declares a conflict with another enabled, installed module is refused (`unavailable`, `Conflicts with <name> (<id>)`) and its library is never opened. The declarer is refused; when both declare it, the higher id, so the result does not depend on discovery order. The module that provides `background` (pin, then profile, whatever its probe says) is never the one refused.
- `[requires] modules = ["<id>"]`: refused with `Needs the module <id>` unless every module named is enabled and installed. Not transitive, so a refusal never spreads.
- A stage's `conflicts`: of two stages that are on and conflict, the declarer wins; when both declare it, the earlier in the order loses; `background` never loses. The rule is the audio worker's, so the two hosts agree. The loser is dropped with a `Warning` and listed `available` false with `Cannot run together with <label>`.
- A stage's `requires` is enforced when the provider is chosen (`Needs <stage>`, `Needs a <slot> stage`); the order check is unchanged. A stage in the `matte` or `post-matte` slot runs only in the module that provides `background`, as one that needs the cut-out already did.
- `GetModules` lists every refusal as `available` false with its reason.

**The override.** `[modules.forced]` (`modules.forced.<id> = true`, video modules only) lifts conflicts, module and stage, for the modules it names, for debugging and testing. It lifts nothing else: a missing required module or stage has no defined behaviour to fall back on, and the placement rule is structural. It is written through `SetConfig` like other choices, so it lives in `config.d/50-panel.toml` and obeys the same file precedence; `modules enable <id> --force` writes it first and then enables, and a plain `enable` clears it so that a debugging choice does not linger. A force is marked in `GetModules`, `modules list` and `modules info`, in the plugin's dialog (which shows the mark and offers no switch), and in `Warning` while it actually overrides a conflict. Audio modules keep `[mic] force_conflicts`.

**Never raw.** A requested background effect that no module can run follows `[effect] on_failure` (`black`, `image`, `none`), for every cause. This supersedes the revision-11 rule, which dropped the effect and showed the camera. Exempting only the provider of `background` from conflicts is not enough: paths still reach the raw picture (a rival that outranks the provider but cannot run the cut-out, a refusal that leaves no provider at the next start), and disabling or a failed probe had always shown the room. With the effect element always present in the output (with no backend and the effect off it passes frames through at no cost), the daemon asks it for the effect even when no module can run it, and the element fails it with its fallback. Mid-session, when the module behind a running effect can no longer run it (disabled, failed re-probe, failed reopen on reload), the element drops its backend instance and shows black or the image from the next frame, the camera staying open; when a module can run it again the effect returns with no restart and reads as loading meanwhile. The switch happens within a frame of the module being disabled, and the camera is never reopened in either direction.

A module refused by a conflict while it runs the session's effect is kept until the session ends, and the refusal applies at the next start as a pin does (`<name> unavailable from the next start: <reason>`); a module that conflicts with it is not opened meanwhile, so two conflicting libraries never share a process.

**Rejected alternatives.**

| Alternative | Why rejected |
|---|---|
| Restart the session under a privacy hold when the effect module is lost | The hold needs the camera to close and open again: a gap of 0.2 to 0.7 s for every application, to do what dropping the instance does in a frame |
| Hold the effect until the session ends whenever its module is lost | A disable would not take effect at once. Kept only for a refusal by conflict, which applies at the next start |
| A probe-aware choice of the module a conflict must not refuse | The conflict is decided before a library is opened, which is the point of it; a probe needs the library loaded, which the conflict forbids. The choice follows pin and profile, and the other side is refused |
| Keep dropping the background effect and protect only its provider | See "Never raw": it closed the conflict path and left the others |
| A force that also lifts requirements and the placement rule | Requirements and placement are structural: a module without a module or stage it needs, or a stage outside the cut-out's module, cannot run, and a force would not make it |
