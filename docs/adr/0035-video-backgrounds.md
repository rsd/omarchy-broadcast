# ADR-0035: Video backgrounds: a decoded video behind the person, handed to the module frame by frame over module ABI 1.4, and for the CPU a still and a conversion command

- **Status:** Accepted (2026-11-13), implemented in daemon 0.43.0 (`crates/obc-module-abi`, `crates/obc-module-sdk`, `crates/obc-module-host`, `crates/obc-backend`, `crates/obc-backend-maxine`, `crates/obc-module-maxine`, `crates/obc-module-onnx`, `crates/gst-obc`, `crates/obc-pipeline`, `crates/obc-ipc`, `crates/omarchy-broadcastd`, `crates/omarchy-broadcast`), D-Bus revision 18, module ABI 1.4. Extends [ADR-0032](0032-background-gallery.md) (the gallery had reserved the video type and said a per-frame background "has its own decision"; this is it) and amends it (the import rules for videos, below). Amends [ADR-0025](0025-loadable-modules.md) (ABI 1.4) and [ADR-0012](0012-video-effects-and-maxine-backend.md) (the background may be a video). Builds on [ADR-0006](0006-on-demand-gpu-lifecycle.md) and [ADR-0017](0017-cuda-checkpoint-parking.md) (nothing at idle), [ADR-0027](0027-output-modes-frame-generation-and-privacy-fallback.md) (the repeat cache), [ADR-0031](0031-onnx-cutout-module.md) (the second `background` provider) and [ADR-0033](0033-system-memory-pipeline.md) (the system-memory path). *Amended (D-Bus revision 19): the daemon no longer makes a VP9 playback copy for the CPU. A video that is not CPU-ready is shown as its poster, a still, with a `Warning` that points at `omarchy-broadcast media convert-command <file>`, which prints the ffmpeg command that converts it into the user's Videos folder; the user runs it. This supersedes the decision below to keep the originals and make a derived copy in the cache, which is kept as alternative D and as a future option. The sections that described the copy now describe the command, and the cache holds posters only.* Reference: [../modules.md](../modules.md#the-per-frame-background-abi-14), [../dbus-api.md](../dbus-api.md#video-backgrounds-revision-18), [../cli-json.md](../cli-json.md#media), [../architecture.md](../architecture.md#video-backgrounds).

## Context
- The `replace` effect shows a still image behind the person. A looping video (a slow gradient, drifting lights, a short animation) is a common wish, and animated GIFs and WebP files are what people already have.
- [ADR-0032](0032-background-gallery.md) built the gallery for stills and kept the fields a video needs in its reply (`type`, `duration_ms`, `poster`). It recorded that a video would be a per-frame background through the module ABI, a change of the ABI and of the effect element with a decision of its own.
- Up to module ABI 1.3 the background reaches a module once, at load time, as a host BGR frame. The cut-out and the composite are one chain inside the module, on the module's own stream, so the daemon cannot composite a video behind the person itself: it would need the matte from every module, which is an ABI break in practice.
- Loading the chain again for each frame is not possible. A switch of the loaded chain blocks the output's streaming thread for tens to hundreds of milliseconds ([ADR-0012](0012-video-effects-and-maxine-backend.md), amendment of 2026-11-13), which is a frame time several times over.
- Where the video is decoded depends on the session's memory ([ADR-0033](0033-system-memory-pipeline.md)). With an NVIDIA GPU, NVDEC decodes H.264, HEVC, VP9 and AV1 at about a tenth of a CPU second for ten seconds of 1080p30. Without one there is no hardware decoder in the pipeline: `vp9dec` (gst-plugins-good, a hard dependency) is the one CPU decoder that is always there. H.264, HEVC and AV1 CPU decoders exist only in an optional package (gst-plugins-bad: `openh264dec`, `libde265dec`, `av1dec`), and there is no `gst-libav` dependency.
- Measured on a development laptop (a Core Ultra 9 275HX, synthetic and deliberately hard content, so a worst case rather than typical footage), per ten seconds of 30 fps video: `vp9dec` at 1080p took about 1.1 to 1.3 CPU seconds (about 12 % of one core) and 4.7 at 4K; H.264 at 1080p took 2.1 to 3.2 (two to three times VP9) and at 4K was slower than real time on one efficiency core; HEVC at 1080p took 3.7 to 4.8; AV1 at 1080p took 1.5 to 2.1. VA-API on the integrated GPU played all four codecs at about 5 % of a core, but the GStreamer `va` plugin is not installed and not a dependency, and on a hybrid machine it opens every render node, including the NVIDIA one, which would break the rule that system memory makes no CUDA call.
- ffmpeg is in Omarchy's base set but is not a package dependency of omarchy-broadcast. A transcode of a 1080p clip of ten seconds to VP9 took about 1.5 to 2.5 seconds on that machine (realtime preset); an estimate, not a measurement, for a four-core low-power CPU is about half to one times the clip's length.
- Every file is untrusted input, read by the daemon as the user it runs as. A video's container and codec are parsed by code that has had many defects, so a file must be checked before a decoder sees it, and the decoder must read the file that was checked.
- The room must never show. A video that cannot play must not become camera frames, the previous still or black frames where a person is expected to be matted; whatever happens to the video, the matte still runs.
- The package may ship only what it may redistribute ([ADR-0032](0032-background-gallery.md)).

## Decision
**A video background is a decode pipeline of its own inside the effect element, played in a loop into a latest-frame slot and handed to the module one frame at a time through a new nullable entry of module ABI 1.4. Imported videos are stored as they are. With CUDA frames the original plays through NVDEC. In system memory the CPU plays only VP9 profile 0 of at most 1920x1080 and 30 fps; any other video is shown as its poster, a still, with a `Warning` that points at `omarchy-broadcast media convert-command <file>`, which prints the command that converts it into a CPU-ready WebM in the user's Videos folder. The daemon makes no copy for playback. D-Bus revision 18 adds no member; revision 19 adds the two that give the command.**

### What is accepted
- **A still** is as before ([ADR-0012](0012-video-effects-and-maxine-backend.md), [ADR-0032](0032-background-gallery.md)): PNG, JPEG or still WebP, 32 MiB, 8192x8192 pixels.
- **A video** is MP4, M4V or MOV (`qtdemux`), or MKV or WebM (`matroskademux`), holding H.264, HEVC, VP9 or AV1, 8-bit 4:2:0, at most 512 MiB and 3840x2160 pixels; the audio is ignored. The container and codec are found from the content, never from the name, by a GStreamer check that decodes nothing (typefind, the demuxer and the parser, bounded to 10 seconds), and the file that was opened for the check is the one that is read (`/proc/self/fd/<n>`), so a path swapped afterwards redirects nothing. The check is the same at `ImportMedia`, at `SetBackgroundImage` (made on the blocking pool, never on the controller's thread, which it could hold for seconds) and in the listing (remembered per file for the daemon's run). A file refused says why.
- **An animated GIF, animated WebP or APNG** is transcoded at import with ffmpeg into a CPU-ready VP9 WebM (the settings of the conversion command below), and the transcode is the item: nothing plays the source. The WebM is stored in the user's Videos folder ([ADR-0032](0032-background-gallery.md)). This transcode stays when the playback copy is gone: it is not a playback copy but the import itself, since the item has to be one file that plays, and a GIF, WebP or APNG is not a video the decoders read. The source's content hash is recorded in the hidden `.sources/` directory of the Videos folder, so the same source is not stored twice. Without ffmpeg it is refused with a reason that says so. Every GIF is treated as an animation, a single frame included.
- **An away image** is a still only ([ADR-0034](0034-away-image.md)); a video or an animation given as one is refused.

### Imported videos are stored as they are
An imported video is copied, as a still is, into the user's Videos folder ([ADR-0032](0032-background-gallery.md)), with the extension of its container, and found again by the SHA-256 of its content instead of its bytes. The user's file is never replaced by a re-encoding, and the daemon never writes a second file for playback. The rule of [ADR-0032](0032-background-gallery.md) that the same bytes are not imported twice therefore keeps working.

### The source in the effect element
- **The pipeline.** `filesrc ! qtdemux|matroskademux ! <parser> ! <decoder> ! videocrop ! cudaconvertscale|videoconvertscale ! NV12 W x H ! appsink`. The demuxer is chosen from the file's first bytes, never by `decodebin`, so only the two demuxers ever read the file; audio pads are never linked. The decoder is chosen from the demuxer's caps and only after the size is known to be within 3840x2160 (the decoded caps are checked again). `videocrop` applies the centred crop to fill, as for a still, and the converter makes the effect's frame size, memory and colour description.
- **A latest-frame slot.** The pipeline runs on its own clock at the video's rate; the appsink keeps one buffer and syncs to the clock. Each **fresh camera frame** hands the backend the slot's newest frame if it has not had it; no rate matching is needed, because a 24 or 25 fps clip is shown for one or two frames of a 30 or 60 fps output, as the output clock repeats camera frames. A **repeat** never advances the video: it is answered from the cache of [ADR-0027](0027-output-modes-frame-generation-and-privacy-fallback.md), so the cache stays valid, and frame generation interpolates between two composited frames as before. A repeat that is processed after a load (a reload puts the load-time still back in the backend) gives the last frame again, so the frame after a reload is never the still.
- **A loop without a gap.** A flushing segment seek to the start once prerolled, then a non-flushing segment seek on each `SEGMENT_DONE`; the slot keeps the last frame meanwhile, so the composite never waits. A clip that prerolls without a frame, or ends three times in a row with none (a zero duration), is a failure and not a loop forever.
- **The slot owns its frames.** Each decoded frame is copied out of the pipeline (on CUDA frames, device to device in the effect's context) before it is kept, so neither the slot nor the effect's last frame given pins one of the decoder's few output surfaces.
- **A lifetime.** The pipeline exists only while `replace` with a video is loaded on a backend that takes per-frame backgrounds. It stops with the element, and, when the video is turned off, once the requested background (a still, blur) is the one loaded; until then the video stays behind the person, never the black or previous still of the chain in force. A flush leaves it playing. It never runs at idle, so the rules of [ADR-0006](0006-on-demand-gpu-lifecycle.md) and [ADR-0017](0017-cuda-checkpoint-parking.md) are unchanged. A source no longer wanted is detached and its decoder's teardown is never waited for on the streaming thread.
- **What stays until the first frame.** Changing the video, or going from a still to a video, reloads nothing: the background in force (the still, or the last frame of the previous video, given again after a reload) stays until the new video's first frame arrives. A video that cannot play keeps it for good. A video chosen with no still has the black still of the chain as its load-time background (`replace` needs no image when there is a video). Neither case is ever black frames in place of the picture or the camera.
- **What the element reports.** Why the video does not play, or that the backend shows it as a still, is `background_error` in the effect statistics and `background-error` in the element's status message (empty while there is none); `background_video` says whether the pipeline exists. A failure is reported once, the first one, and stops the source until it is dropped. The daemon words it for `Warning` (below).

### Module ABI 1.4
`instance_set_background(instance, const obc_frame *background)`, nullable. The host calls it between two `instance_process` calls with an NV12 frame of the chain's output size, colour description and frame kind, and it replaces the background of the following frames until the next call. A host frame is valid during the call; a CUDA frame is valid in stream order (the module may enqueue reads on the chain's stream during the call, and the host keeps the frame alive and unwritten until that work has completed, and nothing may read it afterwards on another stream). A null frame returns to the load-time image, **and so does every load of the chain**, a switch as well as a full reload: the host gives a frame again after a load when it wants one. A failure leaves the previous background in force. A module of ABI 1.3 or older, or one that leaves the entry null, is never called (the host also masks the entry of a library that declares an older minor version, whatever its vtable's size), and shows the video as a still. The contract in full is in [modules.md](../modules.md#the-per-frame-background-abi-14).

The backend seam gains `BackgroundFrame` (a CUDA frame or a borrowed host view), `InferenceBackend::supports_live_background` and `InferenceBackend::set_background_frame`, with the same contract. The Maxine module converts each frame into one of two BGR images of its own with the conversion it uses for the camera, on the chain's stream, so a failure leaves the picture in force and stream order alone keeps a queued composite from reading a half-written image. The ONNX module copies each frame into a buffer it keeps for the chain's life: a host frame directly, a CUDA frame through the frame buffer to the host on the chain's stream, because its composite runs on the CPU in either memory.

### CUDA and system memory
What plays depends on the memory of the session ([ADR-0033](0033-system-memory-pipeline.md)):

| Session memory | Decoders | What plays |
|---|---|---|
| **CUDA** | NVDEC: `nvh264dec`, `nvh265dec`, `nvvp9dec`, `nvav1dec`, sharing the effect's CUDA context, then `cudaconvertscale` into CUDA memory of that context | The original, any accepted video, up to 3840x2160 |
| **System memory** | `vp9dec` only, then `videoconvertscale`; no CUDA element is made and no CUDA call | The original when it is CPU-ready, else the poster as a still |

**CPU-ready** means VP9 profile 0 (8-bit 4:2:0) in WebM or Matroska, at most 1920x1080 and at most 30 fps (a rate the file does not state is not ready). Every animated import and the bundled loops are CPU-ready by construction.

In system memory, by the selected video:

| The selected video | What plays | `Warning` |
|---|---|---|
| CPU-ready | the original, `vp9dec` | none |
| Anything else accepted (H.264, HEVC, AV1; VP9 above 1080p or 30 fps), with a still | the poster as a still | `The video background is shown as a still: it can't play without an NVIDIA GPU; run omarchy-broadcast media convert-command '<path>' for the conversion command` |
| The same, with no still (no poster: an outside file, no ffmpeg) | black behind the person | `The video background plays only with an NVIDIA GPU; run omarchy-broadcast media convert-command '<path>' for the conversion command`, or the element's own `Video background <path> could not be played (<why>)` |

`<path>` is the video's path single-quoted as a shell word, so the line can be pasted; a path that would not fit the 512-byte bound of `Warning` whole and unchanged (a path is never cut), or that is not safe to show as it is, is written `<file>` in its place.

A module whose `background` provider has no per-frame background entry comes first, whatever the memory: it shows the first frame (the poster) as a still, with `<module> shows the video background as a still`. Playing the original on the CPU gives no `Warning`: running on the CPU is a normal state ([ADR-0033](0033-system-memory-pipeline.md)). For none of these cases is anything black or the away image in place of the picture, or the camera: a still or the video is always behind the matte.

One CPU decoder only, `vp9dec`. `openh264dec`, `libde265dec` and `av1dec` are not used even where installed: they are an optional package, so the same file would play on one machine and stand still on another; they cost two to four times VP9 at 1080p; `openh264dec` is single-threaded and is below real time at 4K on one core; and they would be three more decoders of untrusted input inside the daemon.

### Converting a video for the CPU
- **The command, not a job.** The daemon converts nothing for playback. For a video that is not CPU-ready it offers the command: `omarchy-broadcast media convert-command <file>` prints one line, an `ffmpeg` command that writes a CPU-ready VP9 WebM into the user's Videos folder as `<name>-cpu.webm` (the first free `<name>-cpu-<n>.webm`; `-cpu` keeps a WebM input from being overwritten). The user runs it, and the result is listed with the other videos, so it can be chosen at once. The command is `ffmpeg -nostdin -n -protocol_whitelist file -i <input>`, then the very arguments the animated import uses (so there is one set of settings for both), then the output, each path single-quoted so that it pastes into a shell as it is. The daemon never runs it; the output name is made safe as an import's is.
- **The settings.** VP9 profile 0, `yuv420p`, fitted inside 1920x1080 without upscaling with even sizes, at most 30 fps, the first video stream only (no audio, subtitles, data or metadata), a keyframe at least every 2 seconds, the realtime preset (`-deadline realtime -cpu-used 8 -row-mt 1`), constrained quality (CRF 32 under an 8 Mbit/s ceiling; a CRF alone, 28 in the test, made a file 2.7 times the size of its source on the test content).
- **One source for the command.** `GetMedia` gives it for a video item that is not CPU-ready (`convert_command`, with `cpu_ready`), `GetConvertCommand(path)` gives it for any file, and the CLI prints the latter. `Warning` carries only the pointer, never the command: the whole command is about 575 bytes, more than the 512 bytes `Warning` is bound to, and cutting a command makes a command that does something else. A video chosen from outside the gallery (a path in the configuration) has no list row, so `GetConvertCommand` is the way to its command, and the `Warning` names that command with the video's path.
- **`GetConvertCommand` refuses**, as `InvalidArgument` with the reason, a relative path, a file that is not a video or that the check refuses, a video that already plays on the CPU (there is nothing to convert), and a path that is not UTF-8 (a command cannot name it). It runs the same check as `SetBackgroundImage`, off the executor.
- **Untrusted input.** Every ffmpeg run the daemon makes, the animated import and the poster, has the same shape: an argument list and no shell, `-nostdin`, `-protocol_whitelist file`, the demuxer forced to the format the daemon's own check found, the input the very file the daemon opened and checked (handed to the child as its descriptor 3 and named `file:/proc/self/fd/3`), an output path the daemon chose and never overwrites, and the child killed when its parent thread exits, when its time runs out and when the caller cancels. The command given to the user keeps what a pasted line can: `-nostdin`, `-n` (nothing is overwritten) and `-protocol_whitelist file`, with every path quoted; the user runs it as themselves on a file they chose.
- **The cache.** `$XDG_CACHE_HOME/omarchy-broadcast/` (else `$HOME/.cache/omarchy-broadcast/`) holds posters only: `posters/<content hash>.jpg`. The content hash is the SHA-256 of the source, so the same bytes share their poster wherever they live (a video outside the gallery follows the same rule under the same key, so there is one rule and not two) and an edited file gets a new one. Every file is written to a hidden temporary file, synced and renamed, so a name holds a complete file. `RemoveMedia` of a video removes its poster. At the daemon's start a prune removes the `playback/` directory that earlier versions made, whole, the temporary files of interrupted poster runs, and the posters that no gallery video needs (and the outside file the configuration names, if it is a video). A missing or unreadable poster is made again. Everything in the cache can be deleted at any time.

### Posters
A poster is the first frame of a video as a JPEG, at most 1280x720, made with ffmpeg in the cache at import (a failure is logged and is not a refusal). The listing never decodes: it reads the poster that exists, and a video put into the gallery by hand with none is handed to a poster maker (one worker thread, a video at most once at a time, none retried for the same content unless ffmpeg was missing then and is found now); each poster made raises `MediaSerial`, posters that land together raise it once, so a client lists again and finds it. A bundled video ships its poster beside it (`<stem>.poster.jpg`, 640x360, made by the same script, a derived file that is not an item and has no `SOURCES.toml` entry), copied into the cache the first time it is listed, so a bundled loop has one without ffmpeg. The poster is also the still shown for a video the CPU does not play, and the load-time still of a video. Posters are made with ffmpeg because the CPU has no decoder for the first frame of an H.264, HEVC or AV1 file here (the decoders of the pipeline are `vp9dec` only, and none of `gst-libav`, `dav1d`, `openh264dec` is a dependency); an ffmpeg that is not installed leaves the video without a poster.

### The bundled loops
Two procedural loops made by `scripts/gen-backgrounds.sh`, the project's own work (`MIT OR Apache-2.0`, recorded in `SOURCES.toml`): `slow-aurora.webm` and `drifting-bokeh.webm`, VP9 profile 0, yuv420p, 1920x1080 at 30 fps, 10 seconds, no audio, every motion periodic with a period of exactly the clip's length so that the last frame flows into the first. They are CPU-ready, so they play in both memories with no copy. The package installs them and their posters with the stills; ffmpeg is needed only to run the script.

### Dependencies
`ffmpeg` is an optional dependency of the package (animated imports, and posters of imported videos), and the program the conversion command runs. Nothing new is required: `vp9dec` is in gst-plugins-good, the parsers and `webpdec` are where they were. Without ffmpeg, a CUDA machine plays any accepted video and bundled loops and imports videos as they are; it cannot import an animation, make a poster of a video that has none, or run the conversion command.

### Revision 18
No new member. `SetBackgroundImage` and `[effect] background_image` accept a video; `ImportMedia` of a background accepts a video and an animated image; `GetMedia` lists videos with type `video` and their size, `duration_ms` and `poster`; `Warning` gains the clauses of the table above. A client that offers videos checks `InterfaceRevision` (18 or more); an older daemon does not support a video background. (Revision 18 made the copy in the cache and worded `Warning` for it; revision 19 replaced both, below.)

### Revision 19
The daemon stops making playback copies, and the cache's `playback/` directory is removed at the first start. `GetMedia`'s items gain `cpu_ready` (a video only) and `convert_command` (a video that is not CPU-ready, when its path can be named); `GetConvertCommand(s path) -> s` is added; `GetMediaDirs(s kind) -> a{sv}` is added for the gallery's folders ([ADR-0032](0032-background-gallery.md)); and the `Warning` clauses of a video the CPU does not play are the two above. `GetMedia`'s reply keeps its released signature, which is why the folders are a method of their own. A client checks `InterfaceRevision` (19 or more) before it offers the command.

## Consequences
- A video, an animated GIF, WebP or APNG, or a bundled loop is a background on an NVIDIA machine and on one without, and the user's file is not changed by it.
- The cost of a video in a CUDA session is one NVDEC decode, a device copy of each decoded frame into the slot, and, for the Maxine module, one NV12 to BGR conversion per fresh frame on the module's stream. The conversion is negligible next to the cut-out. In a CUDA session a video background costs about as much CPU as a still image, and some additional GPU memory for the decoder; the growth with a 4K clip was not measured. The output held its frame rate in every case measured (synthetic content at 1080p30, a 1080p camera, the development laptop), and a series of fourteen selections of a still, VP9 and H.264 backgrounds and of the blur and replace effects, four seconds apart in one camera session, showed no black frame, no away image and no raw camera frame.
- In system memory a CPU-ready video costs one `vp9dec` decode at 1080p30, about 12 % of one core on the content measured above, beside the cut-out. Any other video costs nothing but the poster. With the ONNX module (CPU engine, MediaPipe landscape model) as the background provider, measured as above (on the development laptop):

  | Background | Daemon CPU | Output |
  |---|---|---|
  | blur | 32.2 % | 30.01 fps, longest gap 50 ms |
  | replace, still image | 25.1 % | 30.01 fps, longest gap 41 ms |
  | replace, VP9 loop | 41.6 % | 29.94 fps, one 124 ms gap in 33 s |

  Playing the video adds 16.5 percentage points of one core over the still. The module's `set_background` takes 0.16 ms per 1080p host frame, and the composite is unchanged. The GPU memory stays at the baseline (no CUDA context).
- A video that is not CPU-ready stands still on a machine without NVIDIA until the user converts it. The first version of this decision made the copy itself, niced and capped at half the logical CPUs, and held 30 fps with a longest gap of 42 ms during a job on a 20 s clip (about 2 s) and on a 60 s 1080p H.264 clip (about 7 s); the maintainer decided that the daemon converts nothing, and the job is not in the code now.
- The gallery's cache, `posters/`, is the daemon's to write, rebuild and prune. The user's files are the user's; the cache is derived and disposable. What the user converts is a file of theirs, in their Videos folder, listed and removed like any other.
- A change of video is never visible as a black frame or a raw camera frame, and a video that fails keeps the picture in force, so privacy does not depend on a decoder.
- Modules of ABI 1.3 or older keep working and show a video as its poster, with a `Warning` that says so.

### Known limits
- **The cache has no size cap.** It holds posters, at most 1280x720 JPEGs, a few tens of kilobytes each, removed with the item and pruned at start, so the question that a playback copy of several hundred megabytes raised no longer arises.
- **A CUDA session copies each decoded frame on the device**, and the module converts or copies it again: a per-frame device copy of the background at the video's rate, kept apart from the decoder's surfaces on purpose (see the slot above). The ONNX module on CUDA frames copies each frame to the host.
- **No VA-API.** A machine whose integrated GPU decodes every codec still shows a non-CPU-ready video as a still. VA-API, through GStreamer's `va` plugin, would play the originals at about 5 % of a core, but on a hybrid machine the plugin opens every render node and is expected to initialise CUDA and NVDEC through the NVIDIA VA driver inside the daemon, which would break the rule that system memory makes no CUDA call, wake the GPU and could block while the process is parked. That was not verified, since the plugin is not installed; it needs its own design (a helper process, or the NVIDIA node excluded).
- **A video the CPU does not play stands still until the user converts it.** Without an NVIDIA GPU the only moving videos are VP9 profile 0 files of at most 1920x1080 and 30 fps, the bundled loops, and the conversions the user makes. This is the price of making no copy.
- **The output name is chosen when the command is printed.** It is the first free `<name>-cpu[-<n>].webm` at that moment, and the command refuses to overwrite (`-n`), so running the same printed command twice writes the file once and stops the second time; print it again for a new name.
- **The first frame of a video is the load-time still** for a module that cannot take frames and for a start with no earlier background, so a module of ABI 1.3 shows a still of the first frame, not black.
- **Hardware decoders are NVDEC only**, and only H.264, HEVC, VP9 and AV1 up to 3840x2160; a stream of 10-bit, 4:2:2 or 4:4:4 is refused at the check.
- **A configured video is checked late.** A video named by `[effect] background_image` is checked on the poster's thread at the camera start; if the check refuses it, the element is given the file all the same and says why it cannot play, and the background is the still in force or black.
- **The loop's seam** with `vp9dec` after the segment seek, and the still-to-video switch in a running session, are covered by tests with the fake backend and, with CUDA, by hardware tests; they have not been measured for a real weak CPU.
- **Drag and drop, a per-effect video and an animated away image** are not implemented.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **A. System memory shows the poster as a still, with a `Warning`** | As the whole rule, a video background would be an NVIDIA-only feature, against the rule that the CPU path is first class ([ADR-0033](0033-system-memory-pipeline.md)), and the bundled loops themselves would stand still. Revision 19 adopts it for the videos the CPU cannot decode only: the bundled loops, every animated import and any video the user converts (the command above) still play, so the CPU path keeps a way to a moving background |
| **B. CPU decoders for H.264, HEVC and AV1 where installed, the poster for the rest** | They are in an optional package, so the same file moves on one machine and stands still on another; they cost two to four times VP9 at 1080p and fall below real time at 4K; three more parsers and decoders of untrusted input in the daemon; no help where the package is missing |
| **C. Transcode every import to VP9 WebM** | It replaces the user's file with a lossy copy for every user, including those with NVDEC who never need it, and cannot be undone; a hash of the source would have to be recorded to keep "never imported twice"; the import becomes slow and asynchronous (a long or 4K clip takes minutes on a weak CPU, and `ImportMedia` is a synchronous call that would need progress); and VA-API could later play the originals almost for free. A derived copy, made only where it is needed, would give the CPU its cheapest measured decoder, keep the originals for NVDEC and later VA-API, and need no progress (the poster is the progress); that was the first decision, and D below replaced it |
| **D. A derived VP9 playback copy made by the daemon in its cache** (the decision of the first version, superseded in revision 19) | It worked and was measured: a job at `nice 19` on half the CPUs held 30 fps beside the cut-out, and the poster stood in until the copy was ready. Superseded by the maintainer's decision that the daemon converts nothing: the user is given the command instead, which makes the same file with the same settings, in a folder the user sees and keeps, and the daemon loses the machinery of the copy (a job queue with cancellation and a failure memory, a settings version in the copy's name, a cache of several hundred megabytes at most, and its prune). It stays a future option: see below |
| **Composite in the daemon** (the module returns the matte, the daemon blends the video) | Every module would have to return its matte, and the composite, the relighting that reads the matte and the HDR look sit inside the module's chain on its stream; an ABI break in practice, and a second composite to keep equal to the first |
| **Reload the chain with a new image for each frame** | A switch blocks the streaming thread for tens to hundreds of milliseconds and holds the engine lock; it cannot run at 30 frames a second |
| **`decodebin` for the video** | It would choose any demuxer and decoder installed for a hostile file; the two demuxers and four codecs are the whole surface, selected from the checked content |
| **`fdsrc` to read the checked file** | It runs in push mode only, where the demuxers take no segment seek, so the loop would not be gapless; `filesrc` on `/proc/self/fd/<n>` reads the very file that was checked |

## What would change this decision
- The maintainer does not mind originals being replaced and accepts a transcode on NVIDIA machines too: alternative C, with CPU-ready files passed through untouched and an asynchronous import, would be simpler.
- Users who run without an NVIDIA GPU want videos to play without a step of their own: the derived copy of D comes back (its design is in the first version of this ADR in the repository history: the same settings, a job in the daemon, `playback/<hash>-v<settings version>.webm` in the cache), with the poster standing in until it is ready, or an option such as `[video] convert = auto` that turns it on.
- `vp9dec` at 1080p30 does not hold beside the cut-out on a weak CPU even at 1280x720: the still on such machines (A), and VA-API moves up.
- `gst-plugin-va` proves safe to load beside a parked NVIDIA GPU and becomes a dependency: direct VA-API playback of the originals first, and the copy only where it is absent.
- A size cap or a quota on the cache, once the storage policy is decided.
- A module ABI 2.0, or a vendor-neutral frame-sharing mechanism (`dmabuf` is reserved): the stream-order rule for CUDA frames would be restated for it.
